faq:
  - question: 'Can I migrate from Keycloak to FoxAuth?'
    answer: "Clients usually move from Keycloak to FoxAuth without much trouble. Users need more planning, because their password hashes do not carry over. Both are OpenID Connect servers, so a client written against Keycloak's token endpoint works against FoxAuth's once the issuer and the client id change. A Keycloak realm maps onto a FoxAuth project more directly than the names suggest: a project is its own issuer, so `https://auth.example.com/acme` publishes its own metadata and mints tokens carrying itself as `iss`, exactly as `/realms/acme` does. A project can also take a subdomain of the instance, such as `https://acme.auth.example.com`, or a hostname of its own. A Keycloak realm cannot: Keycloak's hostname is a server-wide setting, so a hostname per tenant is something you build in front of Keycloak rather than configure in it. A project with an address also signs with keys of its own and publishes them at its own `jwks_uri`, as a realm does. What does not map is the rest of what a realm carries: its authentication flows and mappers. Custom behaviour lives in 31 named override seams (behaviour functions you replace with your own TypeScript), where Keycloak would have you write SPI implementations in Java."
  - question: 'Is FoxAuth lighter to run than Keycloak?'
    answer: 'FoxAuth is a Bun process and one database, PostgreSQL or MongoDB, which is a smaller operational surface than a JVM application server and its relational schema. It starts faster and needs less memory than a JVM server. That difference is real, but it changes nothing about what the protocol endpoints do. Keycloak has years more production hardening behind it, and that is worth weighing against a server whose first stable release, 1.0.0, shipped in October 2026.'
  - question: 'Does FoxAuth support SAML?'
    answer: 'FoxAuth does not support SAML, and none is planned. For sign-in it implements OAuth 2.1 and OpenID Connect only; it also accepts SCIM 2.0 provisioning from a directory, which does not sign anyone in. If an application in your estate can only speak SAML, FoxAuth cannot serve it and Keycloak can, which is a good reason to stay where you are.'
  - question: 'Can an AI agent administer FoxAuth?'
    answer: "An AI agent can administer FoxAuth over MCP, and it uses the same code path a human administrator uses; there is no separate privileged API. Every agent action runs through the console's own routes, permission checks and validation, and lands in the append-only audit trail attributed to the agent. Destructive operations require a second confirming call. The whole surface is off until you set mcp.enabled."

## Moving from Keycloak: no importer, and password hashes do not carry over {#migrating}

There is no importer. Clients are re-registered through the admin API or dynamic registration, and
end-user records are created per project. Password hashes are not portable between the two, so
plan a reset-on-first-login window or run both servers during a cut-over.
