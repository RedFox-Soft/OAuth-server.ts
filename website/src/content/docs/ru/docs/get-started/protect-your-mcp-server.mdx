MCP-сервер, который может вызвать кто угодно, остаётся набором инструментов без входной двери.
Спецификация авторизации MCP добавляет такую дверь, делая MCP-сервер **защищённым ресурсом OAuth 2.1**:
хост агента, обратившийся к нему без токена, получает ответ, где этот токен взять, идёт за ним и
возвращается с токеном, выпущенным для этого MCP-сервера и ни для чего больше.

Вы объявите свой MCP-сервер в FoxAuth, опубликуете с него документ метаданных и ответ `401` с
challenge, проверите один токен, а затем увидите, как MCP-сервер отклоняет анонимный вызов и принимает
авторизованный. На это уйдёт около десяти минут, если у вас уже есть запущенный экземпляр. Если нет,
[запуск через Docker Compose](/ru/docs/get-started/docker-compose/) добавит к ним ещё примерно две.

<Aside
	type="note"
	title="Что нужно заранее"
>
	Запущенный экземпляр с учётной записью администратора ([Создание первого
	администратора](/ru/docs/get-started/first-admin/)) и собственный проект (это
	описано на странице [Регистрация первого
	клиента](/ru/docs/get-started/first-client/)). Ваш MCP-сервер может быть
	заглушкой: пока ему не нужно ничего делать, кроме как отвечать по HTTP.
</Aside>

## 1. Объявите MCP-сервер как ресурс {#1-declare-your-mcp-server-as-a-resource}

Объявляйте его в проекте, у которого есть собственный адрес: путь вроде `/acme`, поддомен вроде
`acme.auth.example.com` или имя хоста. Такой проект сам является издателем (issuer). Идентификатор ресурса уникален только в
пределах своего issuer, поэтому при объявлении ничего с вашего MCP-сервера не загружается и не
проверяется. Он может находиться во внутренней сети, на `localhost`, пока вы разрабатываете, или быть
ещё не развёрнутым. Другой тенант с собственным проектом может объявить тот же URL, никак не затронув
ваш.

Проект без собственного адреса обслуживается корневым issuer экземпляра, общим для всех таких
проектов. В корневом issuer объявить ресурс может только суперадминистратор, потому что собственные метаданные
ресурса не могут сказать, какому из этих проектов он принадлежит.

<Steps>

1. В консоли откройте свой проект и выберите его вкладку **APIs**, затем **New resource**.

2. Заполните три поля.

   **Resource identifier** (идентификатор ресурса): канонический URI вашего MCP-сервера, ровно в том
   виде, в каком его будут называть клиенты, например `https://mcp.example.com/mcp`. Без фрагмента и без
   завершающего слэша: спецификация просит реализации предпочитать форму без слэша, и этот сервер
   хранит идентификатор именно так.

   **Name** (имя): то, что конечный пользователь видит на экране согласия.

   **Scopes it recognises** (распознаваемые scope, то есть области доступа): разрешения, которые
   различают ваши инструменты. Начните с одного, например `mcp:tools-basic`.

3. Настройки токена не трогайте. По умолчанию это самодостаточный токен, который ваш MCP-сервер
   проверяет по опубликованным ключам этого сервера, со сроком жизни пятнадцать минут. Благодаря
   самодостаточному формату разделу 3 ниже, _Проверьте токен_, не нужны собственные учётные данные.

4. Нажмите **Connect** в строке API. В **Connect** собраны значения, которые нужны в следующих разделах, готовые
   к копированию: issuer, точная аудитория его токенов, документ protected resource metadata и строка
   заголовка ответа 401.

</Steps>

<Aside
	type="caution"
	title="Хосты агентов запрашивают все объявленные scope"
>
	Хост агента, не получивший указаний по scope, запрашивает **все** scope,
	которые объявляет ваш ресурс. Так сказано в спецификации, и там же сказано,
	что это задумано: универсальный клиент не может разумно выбирать среди имён,
	которых не понимает. Поэтому каждый клиент, который когда-либо придёт, получит
	весь список, каким бы длинным он ни был. Называйте только те scope, которые
	различают ваши инструменты, а остальные пусть запрашиваются позже.
</Aside>

## 2. Опубликуйте то, что MCP-сервер обязан публиковать {#2-publish-what-an-mcp-server-has-to-publish}

Обе вещи ваш MCP-сервер отдаёт сам: документ метаданных и ответ `401` со ссылкой на этот документ.

### Метаданные защищённого ресурса {#protected-resource-metadata}

JSON-документ по адресу `/.well-known/oauth-protected-resource`, сообщающий, какой сервер авторизации
вас защищает. Спецификация делает его для MCP-сервера обязательным (`MUST`), как и указывающий на него
заголовок `WWW-Authenticate` ниже и проверку audience в разделе 3:

```json
{
	"resource": "https://mcp.example.com/mcp",
	"authorization_servers": ["https://auth.example.com/acme"],
	"scopes_supported": ["mcp:tools-basic"],
	"bearer_methods_supported": ["header"]
}
```

`resource` должен символ в символ совпадать с идентификатором, который вы объявили в разделе 1. `authorization_servers`
называет issuer проекта, в котором вы объявили ресурс: собственный
issuer проекта, если у того есть адрес (`https://auth.example.com/acme`,
`https://acme.auth.example.com` или его имя хоста), и
`ISSUER` экземпляра в остальных случаях. Документ может находиться по адресу
`/.well-known/oauth-protected-resource`, за которым следует путь вашего ресурса, как это формирует RFC
9728, в корне, как выше, или там, куда указывает challenge ниже.

Строка ресурса в консоли показывает, подтверждает ли сейчас этот документ ваше объявление и в каком
из трёх мест он был найден. Эта проверка служит только диагностикой: она ничего не блокирует.

### Challenge, который говорит, куда идти {#a-challenge-that-says-where-to-go}

Когда запрос приходит без токена или с токеном, который вы отклоняете, отвечайте `401` с заголовком
`WWW-Authenticate`, указывающим на этот документ:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         scope="mcp:tools-basic"
```

Параметр `scope` служит любезностью, о которой просит спецификация и которой пользуются клиенты: без него клиент
вернётся к вашему документу метаданных и запросит всё, что перечислено в `scopes_supported`.

## 3. Проверьте токен {#3-validate-the-token}

Ваш MCP-сервер должен установить о каждом токене две вещи: что он подлинный и что он выпущен **для
вас**. Второе не опционально. Принять токен, выпущенный для чего-то другого, значит открыть дыру
confused deputy: ваш MCP-сервер действовал бы с полномочиями, выданными другому сервису. Привязка к
аудитории существует, чтобы закрыть эту дыру, и спецификация прямо запрещает принимать такой токен.

С форматом токена по умолчанию в момент запроса спрашивать у этого сервера ничего не нужно. Один раз
загрузите открытые ключи issuer из `jwks_uri`, объявленного в его метаданных, закэшируйте их и
выполните четыре проверки. Проект с адресом подписывает собственными ключами, поэтому его набор ключей
находится под его собственным issuer (в примере ниже это `https://auth.example.com/acme/jwks`) и не содержит
ключей других тенантов:

```js
import { createRemoteJWKSet, jwtVerify } from 'jose';

const keys = createRemoteJWKSet(new URL('https://auth.example.com/acme/jwks'));

export async function principalFor(authorization) {
	const token = authorization?.replace(/^Bearer /i, '');
	if (!token) return null;

	const { payload } = await jwtVerify(token, keys, {
		issuer: 'https://auth.example.com/acme',
		// The identifier you declared. This is the check that makes the token yours.
		audience: 'https://mcp.example.com/mcp'
	});

	return { subject: payload.sub, scopes: (payload.scope ?? '').split(' ') };
}
```

`jwtVerify` сам проверяет подпись и `exp`; `issuer` и `audience` вы обязаны
указать явно. Любая JWT-библиотека на любом языке выполняет те же четыре проверки. Код выше служит
чек-листом; библиотеку выбираете вы.

<Aside
	type="tip"
	title="Если отзыв должен действовать немедленно"
>
	Самодостаточный токен остаётся действительным до истечения срока, поэтому
	время жизни по умолчанию короткое. Если вашему ресурсу нужно, чтобы отозванный
	токен сразу переставал работать, объявите его с форматом токена **opaque**
	(непрозрачный) и проверяйте каждый токен через [`POST
	/token/introspect`](/docs/reference/endpoints/). Этот эндпоинт требует
	аутентификации, поэтому вашему MCP-серверу понадобятся собственные учётные
	данные и включённый
	[`introspection.enabled`](/docs/reference/settings/#introspection.enabled).
</Aside>

## 4. Дайте хосту агента представиться {#4-let-an-agent-host-identify-itself}

Хост агента обычно не знает ничего, кроме URL, и в нём негде ввести идентификатор клиента. Текущая
спецификация решает эту задачу через **Client ID Metadata Documents**: `client_id` клиента _является_ HTTPS URL,
указывающим на JSON-документ с его описанием. Этот сервер загружает и проверяет документ по
требованию и вообще не создаёт запись клиента.

Может ли хост агента представиться таким способом, показывает вкладка **APIs** проекта. На собственном
сервере такую возможность включает суперадминистратор в **Settings**:
[`clientIdMetadataDocument.enabled`](/docs/reference/settings/#clientIdMetadataDocument.enabled).
Настройка действует сразу после сохранения. Когда она включена, discovery объявляет
`client_id_metadata_document_supported`; клиент проверяет это значение, прежде чем пробовать.

<Aside type="note" title="Старые хосты и что нужно каждой поверхности">
Некоторые хосты агентов умеют только **динамическую регистрацию клиентов**, которую текущая
спецификация помечает как устаревшую, но сохраняет. Она работает: включите
[`registration.enabled`](/docs/reference/settings/#registration.enabled), и такой клиент
зарегистрируется сам, а затем обратится к вашему ресурсу точно так же, как описано выше.

Собственная **административная** плоскость MCP этого сервера на `/mcp` строже. Динамически зарегистрированный клиент никогда не сможет администрировать экземпляр, как бы
ни было настроено всё остальное. Клиент, идентифицированный документом, может, но только после того,
как суперадминистратор укажет его в разделе **Agent access** консоли. Остальные клиенты могут
по-прежнему использовать зарезервированный client id `admin-mcp`, которому запись не нужна.

</Aside>

## 5. Убедитесь, что MCP-сервер отказывает и принимает {#5-prove-it-both-ways}

Сделайте три вызова. Отказы важны не меньше успеха, потому что без них не отличить «защищён» от «до него
просто ещё не дошли».

<Steps>

1. **Вызовите MCP-сервер без токена.** Вы должны получить `401` и заголовок `WWW-Authenticate` из
   раздела 2. Если пришёл `200`, скорее всего, ваша проверка не встроена в путь обработки запроса.

   ```sh
   curl -i https://mcp.example.com/mcp -X POST \
     -H 'content-type: application/json' \
     -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
   ```

2. **Получите токен и вызовите снова.** Направьте хост агента на ваш MCP-сервер и дайте ему пройти
   поток: он должен прочитать ваш документ метаданных, обнаружить этот сервер, выполнить вход вашего
   конечного пользователя и вернуться с токеном. Тот же вызов теперь отвечает `200`.

3. **Попробуйте токен там, где ему не место.** Объявите второй ресурс, получите для него токен и
   предъявите его вашему MCP-серверу. Он должен быть отклонён, потому что claim `aud` не совпадёт.
   Проверка аудитории не даёт токену одной интеграции работать в другой, и хотя бы раз стоит увидеть,
   как она отклоняет токен.

</Steps>

## Чего вам не пришлось делать {#what-you-did-not-have-to-do}

Ни строчки кода в этом сервере и никакого перезапуска ради самого ресурса: объявление хранится как данные,
которые читаются при каждом запросе токена. Никакого секрета клиента для вашего MCP-сервера, потому
что он проверяет токены по опубликованным ключам, ничего не спрашивая у этого сервера. И никакого списка разрешённых
хостов агентов для обычного ресурса: каких конечных пользователей клиент может впустить, следует из
ресурса, который он называет, поэтому ответ на этот вопрос принадлежит проекту, в котором объявлен
ресурс.

Эндпоинты, которых касается эта страница, описаны в [справочнике эндпоинтов](/docs/reference/endpoints/),
а каждая упомянутая выше настройка описана в [справочнике настроек](/docs/reference/settings/), вместе со
значением по умолчанию и обоснованием.
