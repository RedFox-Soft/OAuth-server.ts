An upgrade is five steps. Skip either of the two database steps and you get a deployment that looks
fine and is subtly broken.

<Steps>

1. **Read the changelog.** [The changelog](/changelog/) is kept per release; every entry that needs
   an operator action says so. Releases are also on
   [GitHub](https://github.com/RedFox-Soft/OAuth-server.ts/releases).

2. **Move to the new version.** Change the pinned image tag, or pull the new git tag and rebuild:

   ```bash
   git fetch --tags
   git checkout v<version>
   bun install
   bun run build
   ```

   The published tags are listed on the
   [GitHub releases page](https://github.com/RedFox-Soft/OAuth-server.ts/releases) and on the
   [container package page](https://github.com/RedFox-Soft/OAuth-server.ts/pkgs/container/oauth-server-ts).
   Images are signed and carry an SBOM, so this is the step at which to
   [verify the version you are adopting](/docs/security/assurance/#the-released-image-and-how-to-check-it-is-ours)
   — you are reading the changelog anyway.

3. **Re-run the provisioning step** against the same database:

   ```bash
   bun run db:setup      # MongoDB
   bun run db:setup:pg   # PostgreSQL
   ```

4. **Apply any schema migrations** the release declares:

   ```bash
   bun run db:migrate
   ```

   One command for either datastore. It reports `current` and exits when there is nothing to do,
   which is how most upgrades go. `--plan` lists what would run without running it and exits
   non-zero when work is outstanding, so a pipeline can gate on it before the deploy instead of
   during it.

   A migration that cannot be undone is called out by name before it runs. When you see one, take
   a backup first.

5. **Restart the server.** It refuses to start against a database whose schema is not the one the
   release expects: behind, ahead, or holding a record for a migration whose declaration has since
   changed. A missed step 3 or 4 therefore stops the deploy instead of corrupting data quietly.

</Steps>

<Aside
	type="caution"
	title="Upgrading from before ownership groups"
>
	A deployment old enough to predate ownership groups must upgrade through an
	earlier release first. The one-off conversion that introduced them has been
	retired, and current releases do not attempt it.
</Aside>

## Why step 3 is not optional

`db:setup` is the only thing that applies a release's structural changes. It is also idempotent: it
upserts, so running it against an already-current database changes nothing. What a release can add:

- **New collections** (tables, on PostgreSQL), for a capability that did not exist before.
- **New indexes**, TTL indexes included. A collection that MongoDB auto-creates on first write has
  no TTL index, so documents that were meant to expire simply do not, and nothing complains. The
  script also drops stale expiry indexes for a field a release has stopped writing. On PostgreSQL
  there are no TTL indexes to create; the running server sweeps expired rows itself.
- **Seed changes.** When a release changes the admin seed, `db:setup` is what applies it: a new
  reserved client, a new field on the administrator bucket, a group the ownership model now expects.
  The reserved `admin-mcp` agent client arrived exactly this way. The script carries an explicit
  `$addToSet` for it, because `$setOnInsert` would not touch a project that already existed.

`db:setup` exits non-zero when a constraint it declares is not in force, so make it a gate instead
of a fire-and-forget. The shipped `fly.toml` runs it as `release_command` and Fly aborts the deploy
on failure; the Compose files run it as a `setup` service the server `depends_on` with
`service_completed_successfully`; on Kubernetes it is a Job you wait for.

## Why step 4 is a separate step

`db:setup` only ever adds things: a collection, an index, a seeded document. That is the only kind
of change safe to repeat against a database in any state. Reshaping data that already exists is a
different job. It has to run once, in a declared order, and be recorded so the next deploy knows it
happened. That is what `db:migrate` does, on either datastore, and it is why the two are not one
command.

Three things follow from the record it keeps, and each of them stops a deploy instead of letting it
proceed on a guess:

- A database **behind** this release has outstanding migrations. Run them.
- A database **ahead** of it holds a record for a migration this release does not declare, which
  means the binary is older than the database — a rollback past a migration, usually.
- A database is **diverged** when a migration it already applied no longer matches the one declared
  under that name. A released migration edited after the fact is the cause; the fix is a new
  migration, and the released one stays as it was.

Only one process migrates at a time. A run takes a short renewable lease, so two replicas rolling
at once do not both apply the same step, and a crashed run leaves a lease that expires rather than
a database nobody may touch.

<Aside type="caution">

Re-running `db:setup` does **not** repair a changed `ISSUER`. The console client's redirect URI is
written once, with `$setOnInsert`, when the client is first created. If the public URL of a
deployment has to change, plan for fixing that client's redirect URI through the console (or the
admin API) as part of the change.

</Aside>

## What a restart carries, and what it does not

- **Server settings are already in force.** A change saved in the console takes effect in the
  instance that saved it, so an upgrade neither applies nor re-applies it: the stored settings are
  simply read again at startup. An upgrade is still a good moment to re-read the
  [settings reference](/docs/reference/settings/) for anything the release added. A setting that
  genuinely cannot be applied to a running server says so on its card and in the console, and there
  are none at present.
- **Signing keys persist in the database**, through the `jwksStore` adapter, and are loaded once at
  startup. An upgrade neither rotates nor invalidates them: tokens issued before it still verify,
  and `/jwks` serves the same key set. Keys are not environment configuration and there is nothing
  to carry across by hand.
- **SMTP settings** are read live from their own store on every send, so they are unaffected by a
  restart in either direction.
- **Tokens, sessions and grants survive**, since they live in the database. Users are not signed
  out by an upgrade, with one release-specific exception below.

## One upgrade signs your end users in again

Upgrading **to the release that made user buckets addressable**, and only that one, ends every
end-user sign-in once.

A sign-in is held in a browser cookie, and that cookie is now named after the bucket it belongs to —
`_session_default`, `_session_acme` — so that somebody can be signed in to two buckets at once
without either sign-in disturbing the other. Cookies written before the upgrade carry the old,
bucket-less name. They are not read, and the server expires them on the first request that presents
one, so a browser stops sending a cookie that no longer means anything.

What your end users see: the sign-in screen, once, the next time they visit. Nothing is lost —
accounts, grants, consent and refresh tokens are all untouched, and a refresh token keeps working
without anybody signing in at all. There is nothing to do on your side and no order to do it in;
it is listed here so the support question is expected rather than alarming.

The console is unaffected in one respect worth naming: it stays at `/admin`. An earlier plan moved
it to free that word for a bucket address, and that turned out not to be necessary — the
administrators bucket is served at the root and never puts its name in a URL.

## After the restart

```bash
curl -sf https://auth.example.com/ready
curl -s https://auth.example.com/.well-known/openid-configuration | jq -r .issuer
```

`/ready` rather than `/health` on purpose: `/health` answers for the process alone and would pass
against a server that came up unable to reach its database. The second is the check worth
automating. The shipped deploy workflow does exactly this, because the advertised issuer is the
value a deploy can get wrong without anything else noticing.

Then open `/admin` and sign in. That single act exercises the seed, the console client, the
administrator bucket and the authorization code flow at once, so if it works, the upgrade landed.
Super administrators should also glance at **Faults**. Only genuine defects are recorded there,
never routine client rejections, so anything new after an upgrade is probably worth reading.
