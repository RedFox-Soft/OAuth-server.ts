MCP-серверу, который сам проверяет токены, нужен для этого код. Он загружает ключи проекта, проверяет каждый токен,
отвечает `401` с нужным заголовком и публикует документ, который говорит агентам, где войти. Этот код разобран на
странице [Защита MCP-сервера с помощью OAuth](/ru/docs/get-started/protect-your-mcp-server/). Здесь показан способ
обойтись без него.

Ваш обратный прокси (Caddy, Traefik или nginx) стоит перед MCP-сервером. Прежде чем пропустить запрос к серверу,
прокси просит ваш проект FoxAuth его проверить. Проект проверяет токен и права, которые нужны вызванному инструменту.
До MCP-сервера доходит только запрос, прошедший проверку. Право (scope) означает одно именованное разрешение в токене,
например `files:read`.

Если прокси уже обслуживает MCP-сервер, на всё уйдёт около десяти минут.

## Что проверяет прокси {#what-the-proxy-checks}

О каждом запросе прокси спрашивает проверку проекта по адресу вида
`https://auth.example.com/acme/verify/api/<checkId>`. Проверка берёт токен из заголовка запроса
`Authorization: Bearer`. Она принимает токен, только если выполнено всё, что проверил бы сам MCP-сервер:

- токен подписан собственными ключами проекта;
- токен выпустил этот проект;
- токен выпущен для этого MCP-сервера и ни для какого другого (его аудитория);
- срок токена не истёк, и время начала его действия уже наступило;
- это токен доступа, а не ID-токен.

Проект может выдавать и непрозрачные (opaque) токены. Это случайная строка, внутри которой ничего нельзя прочитать.
Такой токен проверка ищет в проекте и принимает, только пока его срок не истёк и его не отозвали.

Запрос без токена или с токеном, который не прошёл проверку, получает `401`. Заголовок `WWW-Authenticate` в ответе
называет документ, который говорит агенту, где войти. Этот документ называется метаданными защищённого ресурса
(protected resource metadata, RFC 9728), и его публикует за вас проект. Вашему MCP-серверу не нужно ничего отдавать
для входа.

## 1. Объявите API с ответом «Your proxy» {#declare-the-api}

1. Откройте проект, перейдите на вкладку **APIs** и нажмите **New resource**.
2. Заполните поля:
   - **Resource identifier**: адрес, который вызывают агенты, например `https://mcp.example.com/mcp`. Это должен
     быть адрес `https`, потому что проверка сравнивает его хост с хостом, о котором сообщает прокси.
   - **Name**: это название люди видят на экране согласия.
   - **Scopes**: права, которые различают ваши инструменты, например `files:read`, `files:write` и `files:delete`.
   - **Who checks tokens?**: выберите **Your proxy**.
3. Посмотрите на настройки токена. Отозванный самодостаточный токен работает на прокси, пока не истечёт его срок
   (подробнее в разделе [Отозванный токен](#revocation) ниже). Поэтому выберите **Opaque** или сделайте срок жизни
   коротким.

Существующий API тоже можно переключить на **Your proxy** в форме его изменения. Токены, выданные до переключения,
работают, пока не истечёт их срок.

## 2. Настройте прокси {#configure-your-proxy}

Нажмите **Connect** в строке API. Там есть адрес проверки, адрес метаданных и конфигурация для вашего прокси, в
которую уже подставлены ваши адреса. Копируйте её оттуда. Примеры ниже содержат тот же текст, и строит его тот же
код. Они показаны для MCP-сервера по адресу `https://mcp.example.com/mcp` в проекте по адресу
`https://auth.example.com/acme`. Вместо `<checkId>` будет идентификатор проверки вашего API.

Каждая конфигурация делает три вещи:

- Сначала она отправляет каждый запрос на проверку, вместе с исходным методом и хостом запроса.
- Она удаляет все заголовки `X-Auth-*`, которые прислал клиент, чтобы никто не выдал себя за другого.
- Она передаёт запрос MCP-серверу с заголовками, которые вернула проверка. Заголовок `Authorization` проходит без
  изменений.

Считается, что сам MCP-сервер слушает `127.0.0.1:8080`. Замените этот адрес на настоящий.

### Caddy {#caddy}

	kind="caddy"
	target="api"
/>

Блок `route` сохраняет порядок директив. Без него Caddy удалил бы заголовки `X-Auth-*` уже после того, как их
установила проверка. Когда проверка отказывает, `forward_auth` передаёт её ответ клиенту вместе с заголовками.

### Traefik {#traefik}

<ProxyRecipe
	kind="traefik"
	target="api"
/>

Это динамическая конфигурация для файлового провайдера. `authResponseHeadersRegex` удаляет все заголовки
`X-Auth-*`, которые прислал клиент, и копирует те, что вернула проверка. Когда проверка отказывает, Traefik
передаёт её ответ целиком.

### nginx {#nginx}

<ProxyRecipe
	kind="nginx"
	target="api"
/>

`auth_request` в nginx понимает только три ответа: «разрешено», `401` и `403`. При `401` nginx сам передаёт клиенту
заголовок `WWW-Authenticate` из ответа проверки. При `403` он этого не делает, поэтому `map` в начале добавляет
заголовок обратно. Именно из этого заголовка клиент узнаёт, какие права нужны инструменту. `map` должен стоять в
контексте `http`, а файл в `conf.d` уже находится в нём. Добавьте строки с сертификатом там, где указано в
комментарии.

## 3. MCP-сервер должен быть доступен только через прокси {#reachable-only-through-the-proxy}

Проверка защищает только те запросы, которые проходят через ваш прокси. Запрос, который дошёл до MCP-сервера в
обход прокси, никто не проверяет, и сервер поверит любому заголовку `X-Auth-*` в нём.

Поэтому пусть MCP-сервер слушает только там, где до него может дотянуться прокси: на `127.0.0.1`, в частной сети или
за правилом межсетевого экрана, которое пропускает только прокси.

## 4. Что получает MCP-сервер {#what-your-server-receives}

Когда запрос пропущен, прокси добавляет к нему такие заголовки:

| Заголовок        | Что в нём                                                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-Auth-Subject` | От чьего имени действует токен: его `sub`. Для токена программы без человека это идентификатор клиента.                                       |
| `X-Auth-Client`  | Идентификатор клиента, у которого этот токен, например хоста агента.                                                                          |
| `X-Auth-Scope`   | Права токена через пробел.                                                                                                                    |
| `X-Auth-Reason`  | Короткий код решения: `allowed` или `preflight` для CORS-проверки браузера. В ней нет токена, поэтому остальные заголовки пустые.             |
| `Authorization`  | Исходный токен без изменений. Он нужен серверу, который обменивает его на токены человека в другом сервисе. Сервер может и сам его проверить. |

## 5. Укажите, какие права нужны каждому инструменту {#tools}

Без таблицы инструментов любой действительный токен может вызвать любой инструмент. Чтобы задать таблицу, нажмите
**Tools…** в строке API.

MCP-клиент, который следует спецификации MCP от 2026-07-28, сообщает, что он делает, в двух заголовках:
`Mcp-Method` (например, `tools/call`) и `Mcp-Name` (инструмент). Проверка читает их, поэтому в таблице можно указать,
какие права нужны каждому инструменту:

| Инструмент     | Нужные права                  |
| -------------- | ----------------------------- |
| `search_files` | `files:read`                  |
| `delete_file`  | `files:write`, `files:delete` |

Права выбираются из собственных прав API. С такой таблицей:

- Вызов `delete_file` с токеном, в котором есть только `files:write`, получает `403`. Заголовок `WWW-Authenticate`
  содержит `error="insufficient_scope"` и перечисляет все права, нужные инструменту: `files:write files:delete`.
  Клиент может запросить ровно их.
- Для списка инструментов (`tools/list`) нужен только действительный токен, поэтому клиент всегда видит, что ему
  можно вызвать.
- Вызов `tools/call`, в котором не назван инструмент, отклоняется.
- Имена инструментов сравниваются точно: `Delete_File` и `delete_file` считаются разными именами.

Под таблицей есть два выбора:

- **Any other tool**: инструмент, которого нет в таблице, отклоняется, или для него нужен только действительный
  токен. По умолчанию он отклоняется.
- **Clients too old to say which tool they call**: клиент, который не присылает `Mcp-Method` или говорит на версии
  протокола старше 2026-07-28, по умолчанию отклоняется. Его можно пустить, но тогда он сможет вызвать любой
  инструмент.

### Чего таблица не охватывает {#what-the-table-does-not-cover}

- Для чтения ресурса (`resources/read`) и получения промпта (`prompts/get`) нужен только действительный токен.
  Таблица называет только инструменты.
- Прокси видит заголовки, но не тело запроса. Ваш MCP-сервер по-прежнему должен отклонять запрос, в котором
  заголовок `Mcp-Name` и тело называют разные инструменты. Этого требует от серверов спецификация MCP. Поэтому же
  старые клиенты по умолчанию отклоняются: их серверы эти два значения не сравнивают.

## Ограничения {#limits}

### Отозванный токен работает, пока не истечёт {#revocation}

В самодостаточном токене есть всё, что нужно проверке, поэтому она не спрашивает проект, отозван ли токен. Такой
вопрос добавил бы чтение из базы данных к каждому вызову. Поэтому отозванный самодостаточный токен работает на
прокси, пока не истечёт его срок. По умолчанию срок жизни пятнадцать минут. Если отзыв должен срабатывать сразу,
выдавайте непрозрачные токены: проверка ищет каждый из них, и отозванный токен отклоняется на следующем запросе.

### Токены, привязанные к ключу, отклоняются {#bound-tokens}

Некоторые токены работают только вместе с ключом, который хранит клиент, через DPoP или клиентский сертификат
(mTLS). Доказательство владения ключом относится к запросу, который клиент отправил вашему MCP-серверу, а прокси
передаёт дальше только заголовки. Поэтому проверка не может подтвердить ключ. Такие токены она отклоняет с `401` и
причиной `bound_token_unsupported`. Как обычные токены она их не принимает.

### В отказах нет заголовков CORS {#cors}

Браузер позволяет странице с другого сайта прочитать ответ, только если в ответе есть заголовки CORS. В ответах
`401` и `403` от проверки их нет. Поэтому MCP-клиент, работающий в браузере, не сможет прочитать
`WWW-Authenticate` из отказа, если только ваш прокси не добавляет заголовки CORS к ошибкам. Сама CORS-проверка
браузера (`OPTIONS` с `Access-Control-Request-Method`) не несёт токена и пропускается, так что на неё отвечает ваш
MCP-сервер.

### Токен может получить любой, кто может войти в проект {#who-can-get-a-token}

В этом режиме проверяется токен, а не то, кто этот человек. Любой, кто может войти в проект, может получить токен
для этого API, а ограничения по группам в этом режиме нет. Чтобы ограничить, кто может вызывать API, ограничьте, кто
может войти в проект.

## 6. Убедитесь, что всё работает {#check-that-it-works}

1. Вызовите MCP-сервер без токена:

   ```sh
   curl -i https://mcp.example.com/mcp -X POST \
     -H 'content-type: application/json' \
     -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
   ```

   Должен прийти `401` с заголовком `WWW-Authenticate: Bearer resource_metadata="…"`. Если пришёл ответ самого
   MCP-сервера, запрос не прошёл через проверку.

2. Откройте адрес из `resource_metadata`. Поле `resource` в нём совпадает с идентификатором вашего API, а
   `authorization_servers` называет ваш проект.

3. Направьте хост агента на ваш MCP-сервер. Он прочитает этот документ, проведёт вход человека в проекте и вернётся
   с токеном. Тот же вызов теперь доходит до вашего сервера, с заголовками `X-Auth-*`.

Включать ничего не нужно. Это доступно на любом тарифе.

Как пускать к API только некоторые группы, только из вашей сети или в ваши часы, смотрите в разделе [Условия на вашем
прокси](/ru/docs/get-started/add-conditions-at-your-proxy/).
