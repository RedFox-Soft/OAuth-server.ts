Клиент — это приложение, которое запрашивает у этого сервера токены. В консоли он называется
**приложением** (application). Каждое приложение живёт в бакете пользователей, а каждый бакет
принадлежит группе. Это три понятия, но они вложены друг в друга, поэтому консоль проводит по ним
по порядку.

## Группы, бакеты, приложения {#groups-buckets-applications}

- **Группа** чем-то владеет. У каждого бакета пользователей есть группа-владелец, и именно членство
  в этой группе даёт доступ к бакету и всему, что в нём есть. Отдельного списка назначенных
  управляющих нет. У каждого администратора уже есть группа **Personal**, и для первого клиента её
  обычно вполне достаточно; группа типа **regular** — это компания или команда, общая с коллегами.
- **Бакет пользователей** — это совокупность конечных пользователей: их учётные записи и политика
  того, как они регистрируются и подтверждают себя. В нём же лежат **приложения**, через которые
  эти люди входят, и **API**, для которых они получают токены. Созданный вами бакет — это ещё и
  тенант со **своим собственным издателем (issuer)**: он обслуживается по адресу `<ISSUER>/<slug>`
  или по собственному имени хоста и выпускает токены с этим issuer, поэтому приложение в нём
  интегрируется с этим адресом, а не с корневым. Исключение — бакет по умолчанию `redfox`: он
  сохраняет корневой issuer, и именно это позволяет существующему развёртыванию остаться как есть.
- **Приложение** — это OAuth-клиент. Оно принадлежит бакету, в котором создано, всю свою жизнь;
  перенести его в другой бакет нельзя никакой операцией.

<Steps>

1. **Выберите группу.** Диалог создания бакета спрашивает, в какую группу его поместить, и
   начинает с группы, выбранной вверху консоли. Для первого клиента подойдёт ваша группа
   **Personal**, но в ней ровно один член, поэтому общую работу стоит вести в обычной группе: создайте
   её в разделе **Groups** или перенесите работу туда позже.

2. **Создайте бакет** в разделе **Buckets**. Для него нужны имя и адрес: путь, который становится
   последней частью issuer в его токенах, или собственное имя хоста. Выбирайте адрес обдуманно:
   идентификатор issuer — это обещание, данное каждому клиенту, настроенному на него, поэтому смена
   адреса позже сначала показывает, что затронет, и требует подтверждения — она касается каждого
   приложения в бакете. Новый бакет закрыт для регистрации, если не выбрать **Anyone who can reach
   the sign-in page**; изменить это можно позже на его вкладке **Sign-in**.

   В таблице Buckets адрес каждого бакета показан в столбце **Address**. У зарезервированных бакетов
   там вместо пути написано _served at the root_, поскольку они сохраняют корневой issuer. Добавлять
   приложения в бакет по умолчанию `redfox` может только суперадминистратор, а в бакет
   администраторов — никто.

3. **Создайте клиента** на вкладке **Applications** бакета кнопкой **New client**. Выберите тип
   приложения и метод аутентификации на эндпоинте токенов, затем введите redirect URI. Этому выбору
   посвящён следующий раздел. Если к эндпоинту токенов будет обращаться браузерный код с другого
   origin, укажите этот origin в поле **Browser origins**; список можно скопировать из другого
   приложения того же бакета.

</Steps>

## Публичный или конфиденциальный {#public-or-confidential}

Выбор сводится к **методу аутентификации на эндпоинте токенов** (token endpoint auth method), и он
следует из того, может ли ваше приложение хранить секрет:

| Метод                     | Для чего                                                                                   | Учётные данные                                   |
| ------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| `none` (публичный / PKCE) | SPA в браузере, мобильные и десктопные приложения, CLI: всё, что поставляется пользователю | Нет. Доказательством служит PKCE.                |
| `client_secret_basic`     | Серверные веб-приложения и бэкенд-сервисы                                                  | Секрет, передаваемый в заголовке `Authorization` |
| `client_secret_post`      | То же самое, когда клиентская библиотека может передать учётные данные только в теле формы | Секрет, передаваемый в поле формы                |

PKCE здесь не опционален ни для одного из видов. Любой запрос авторизации с `response_type=code`
без `code_challenge` отклоняется, а единственный принимаемый метод — `S256`. Запрос с `plain`
отклоняется, и discovery объявляет только `S256`. Поэтому публичный клиент без секрета — вовсе не
более слабый клиент: полученный им код бесполезен для любого, кто не генерировал verifier.

<Aside type="caution" title="Секрет показывается один раз">

Когда создаётся конфиденциальный клиент или когда вы выполняете ротацию его секрета из таблицы
клиентов, значение появляется в диалоге с текстом «Copy this secret now — it will not be shown
again.» Восстановить его потом нельзя. Единственный путь назад — ротация, которая делает старый
секрет недействительным.

</Aside>

## Redirect URI сравниваются точно {#redirect-uris-match-exactly}

Redirect URI должен быть зарегистрирован, а `redirect_uri` из запроса сравнивается с
зарегистрированным набором **как написано**: схема, хост, порт, путь и query должны совпадать.
`https://app.example.com/cb` и `https://app.example.com/cb/` — два разных URI.

Есть ровно одно послабление — то, которого требует RFC 8252 §7.3: клиент с типом приложения
**native**, перенаправляющий на `http:` на loopback-хосте, может использовать любой порт. Всё
остальное по-прежнему должно совпадать точно. Послабление намеренно узкое:

- только для native-клиентов; redirect веб-клиента — это реальный хост под его контролем, так что
  ничего эфемерного в нём нет;
- только `http:` на loopback-хосте; redirect на закреплённый за приложением (claimed) `https`-адрес
  или на приватную схему по-прежнему сравнивается точно;
- `localhost` и `127.0.0.1` **не** считаются взаимозаменяемыми. Зарегистрируйте обе формы, если
  ваш клиент может использовать любую из них.

Открытой остаётся гонка за локальный порт: другой процесс на машине пользователя может занять порт
и получить код. Её закрывает PKCE — именно поэтому он обязателен.

## Каких пользователей впускает клиент {#which-users-a-client-signs-in}

Маршрутизация входа определяется бакетом, которому принадлежит клиент, и никогда — самим клиентом:

1. зарезервированный клиент консоли всегда направляется в бакет администраторов;
2. приложение, созданное в бакете, направляется в **этот бакет**;
3. клиент, динамически зарегистрированный по адресу бакета (его `/reg`), принадлежит этому бакету;
4. запрос, который называет один API, объявленный по адресу, куда пришёл запрос, направляется в
   бакет этого API;
5. всё остальное (клиент, зарегистрированный в корне, или клиент, заданный документом метаданных)
   направляется в бакет по умолчанию `redfox`.

Приложение бакета по умолчанию `redfox` к нему не привязано: правила 4 и 5 к нему по-прежнему
применяются.

Бакет — это ещё и место, где живёт политика онбординга: открыта ли регистрация
(`registrationOpen`), должна ли новая учётная запись подтвердить e-mail
(`emailVerificationRequired`), происходит ли это по ссылке или по шестизначному коду
(`verificationMethod`), предлагается ли вообще вход по паролю (`passwordLogin`) и обязательно ли
приложение-аутентификатор (`totpRequired`). Ничего из этого не задаётся на клиенте. Два приложения в
одном бакете разделяют всё это, потому что разделяют учётные записи.

<Aside type="note">

Согласие включено по умолчанию (`consent.require` для нового клиента по умолчанию равно `true`),
поэтому первый запрос авторизации покажет экран согласия. Исключение — зарезервированный клиент
консоли: это собственный (first-party) клиент, и он этот экран пропускает.

</Aside>
