The token that opened every tool on the MCP server had been issued for the internal wiki.

The server did what most first attempts do. It fetched the identity provider's public keys, checked
the signature and the expiry, read the subject out of the payload and called it authenticated.
Every one of those checks passed, because the token was genuine. It was a perfectly good token for
the wiki, and the MCP server never asked who it was for. Anyone holding any token from that provider,
for anything, could list and call the tools as whoever the token named.

That is the bug the MCP authorization specification exists to prevent, and once you see it, the rest
of the specification stops looking like a new protocol and starts looking like what it is: an
ordinary OAuth 2.1 resource server, with the discovery steps written down so that a client that
knows nothing but a URL can find its way to a token. I have spent a fair amount of time on the
authorization-server side of it, and my summary is that it is three documents and one claim, and
almost every real problem is in the one claim.

## Three documents and one claim

The agent host knows one thing: the URL of your MCP server. From there it has to learn who
protects you, how to talk to that authorization server, and how to identify itself, and then it has
to come back with a token that is for you and nobody else. Each of those is a document, and the last
is a claim in the token.

Step 2 is the only part of all this that the specification makes a MUST for an MCP server, and it is
two lines. When a request arrives with no token, or with one you reject, you answer 401 and say
where your metadata is:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         scope="mcp:tools-basic"
```

And the metadata itself is a JSON document, RFC 9728, that says who protects you:

```json
{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://auth.example.com/acme"],
  "scopes_supported": ["mcp:tools-basic"],
  "bearer_methods_supported": ["header"]
}
```

Everything after that is the authorization server's problem and the client's. The client takes the
issuer from the document, fetches that server's metadata by the well-known forms RFC 8414 and OpenID
Connect Discovery define, and it has to try both, because the specification only requires the server
to publish one. Then it runs an ordinary authorization code flow with PKCE, and in both the
authorization request and the token request it sends one parameter that is not ordinary at all in
practice, even though it has had an RFC since 2020.

## The resource parameter is the whole point

RFC 8707 lets a client say what it wants the token for. The MCP specification makes it mandatory in
both requests, and it is what turns "a token from the provider" into "a token for this MCP server".
The authorization server mints the token with that URI as its audience, and the MCP server refuses
any token whose audience is not exactly its own identifier. That is the line the wiki token failed
at, and it is the only line that would have stopped it.

Here is what the server hands back for the flow above, decoded:

```json
{
  "iss": "https://auth.example.com/acme",
  "aud": "https://mcp.example.com/mcp",
  "sub": "248289761001",
  "client_id": "https://host.example/client.json",
  "scope": "mcp:tools-basic",
  "iat": 1759226400,
  "exp": 1759227300,
  "jti": "o1S6Qw3bH9c_UZL0"
}
```

The check on the MCP server's side is four claims, and two of them are ones you have to state
yourself, because a JWT library cannot guess them:

```js
import { createRemoteJWKSet, jwtVerify } from 'jose';

const keys = createRemoteJWKSet(new URL('https://auth.example.com/acme/jwks'));

export async function principalFor(authorization) {
	const token = authorization?.replace(/^Bearer /i, '');
	if (!token) return null;
	const { payload } = await jwtVerify(token, keys, {
		issuer: 'https://auth.example.com/acme',
		audience: 'https://mcp.example.com/mcp'
	});
	return { subject: payload.sub, scopes: (payload.scope ?? '').split(' ') };
}
```

The signature and `exp` are the library's. `issuer` and `audience` are yours, and the second is the
one the first attempt left out. Any library in any language does the same four checks; the shape is
the checklist.

What took me longer to appreciate is that the same string now appears in three places that were
written by three different parties, and it has to be the same string in all of them. The MCP server
publishes it in its metadata as `resource`. The operator of the authorization server declares it as
the identifier of a protected resource. The client sends it as `resource` and the token carries it as
`aud`. The comparison is exact, after canonicalization, and it is exact on purpose: no prefix match,
no "a token for the parent path is good for the child", because that is precisely how one
integration's token ends up working at another's.

Canonicalization is where the first version of ours had a bug that reasoning found and the tests did
not. The specification says clients should use the form without a trailing slash, and that servers
should accept an uppercase scheme or host, so we canonicalize both the declaration and the request
through one function, and that function takes an option for a resource whose slash is meaningful.
The bug was that the comparison canonicalized the request with the default options while the
declaration had been stored with the slash kept, so the slash was stripped from one side only and a
resource that declared the slash significant collapsed into its slash-free sibling. Both sides have
to go through the same function with the same options, and if that sounds obvious, it was obvious to
me too, after.

The other thing I would say about the audience is that it is the whole of what makes a declared
resource safe to be data. In our server, declaring an MCP server is a form in the console: an
identifier, a name for the consent screen, the scopes it recognises. Nothing is restarted and no
code changes, and the declaration is read on every token request, with no cache in front of it,
because a deleted declaration has to stop issuance on the next request rather than after some
memo expires. We had already learned that lesson once, with a client cache that served a stale
client to the admin plane, and did not need to learn it again.

## Who the client is, when there is nobody to type a client id

The agent host has a URL and nowhere for you to paste a client identifier. The specification's first
answer used to be dynamic client registration: the client POSTs a description of itself, gets a
`client_id` back, and the authorization server accumulates a row per host that ever connected. The
current revision marks that deprecated and puts Client ID Metadata Documents first, which I think is
the right call and also the part of the specification most worth being nervous about.

The idea is that the `client_id` is itself an HTTPS URL, and at that URL sits a JSON document
describing the client:

```json
{
  "client_id": "https://host.example/client.json",
  "client_name": "Example Agent Host",
  "redirect_uris": ["http://127.0.0.1:52123/callback", "https://host.example/oauth/callback"],
  "token_endpoint_auth_method": "none",
  "grant_types": ["authorization_code", "refresh_token"]
}
```

The authorization server fetches it on demand, validates it, and stores nothing. No registration
endpoint, no table of clients that grows by one per laptop, and the client's name on the consent
screen comes from a document the client's operator controls at a domain they demonstrably hold.

What that costs is that an unauthenticated stranger can now make your authorization server issue an
HTTP request to a URL of their choosing. Every mitigation for that has to be on the server, and ours
is one module that knows about the network and nothing else: it refuses private, loopback and
link-local address ranges by comparing addresses as numbers rather than as text, because the URL
parser will happily rewrite an IPv4-mapped IPv6 address into a form a string check misses; it
follows redirects by hand and re-checks every hop; it stops reading at five kilobytes; and it is
bounded in time. The feature is off by default, and the reason is exactly that sentence about the
stranger. Once the document is in hand, the checks are short and each one closes a specific trick:
the `client_id` inside the document must equal the URL byte for byte, so that hosting a document
naming somebody else's identifier gets you nothing; `redirect_uris` must be present and non-empty;
a symmetric client secret is refused, because a secret in a world-readable document is not one; and
a key-based authentication method must say where its keys are.

The part I would call genuinely unresolved is loopback. A native agent host listens on
`127.0.0.1` on some port for the callback, so its document lists a loopback redirect. The document
proves that whoever wrote it controls the domain. It cannot prove which local process is listening
on that port. An attacker on the same machine can present the real host's `client_id`, bind their
own port, and the user sees the real host's name on the consent screen. The specification knows
this, says the server should warn, and leaves it there. For an ordinary resource we carry that risk
the way everyone does. For the one place a document-identified client can hold administrative
authority over the authorization server itself, we turned the warning into an interlock: a document
offering only loopback redirects cannot be permitted until an administrator acknowledges, in words,
what that does not prove.

## Which users an agent signs in

Here is a question the specification does not ask, because it assumes one authorization server
protects one MCP server for one population of users, and that is not what an authorization server
looks like once more than one team uses it.

Suppose the server hosts several tenants, each with its own users, and an agent host arrives
identified by a metadata document. It belongs to no tenant. It is a URL. Whose users does it sign in?
The answer we settled on is that the resource decides: an administrator of a tenant declared that MCP
server in a project of theirs, and a request naming that resource signs into that project's users.
That is safe for a reason worth stating precisely. The client did not create the option, an
administrator did, in a project they own, so the parameter selects among an operator's declarations
and cannot manufacture one.

It was safe, that is, against attackers without a console account. Anyone with one could declare
anything, identifiers were unique across the whole instance, and first won. So a hostile tenant
could declare somebody else's MCP server, leave the real owner a permanent conflict, and route that
server's users into their own bucket. The first fix made every declaration prove itself by fetching
the resource's own metadata and checking that it named this issuer, which is the natural fix and
also refused every MCP server on an internal network, on localhost during development, or not
deployed yet. It lasted a day.

What replaced it is namespaces, and it is the arrangement I would now recommend to anyone building
this. A tenant with an address of its own is its own issuer, with its own signing keys, and a
resource identifier is unique only within an issuer. Two tenants may declare the same MCP server
and neither ever sees the other's declaration, because every resolution reads only the namespace of
the address the request arrived at. A declaration in your own namespace makes no outbound request
at all, since it can only be a claim about your own users. And the one namespace that is genuinely
shared, the root issuer that every tenant without an address is served at, accepts declarations from
a super administrator only, because there a resource's metadata can say it trusts the issuer and
still cannot say which of those tenants it belongs to. No proof closes squatting there, so nobody
but the operator gets to try.

Three more holes in the same area. The first two have the form "a caller forgot to pass the
resource", and both are worth knowing because they are the kind of thing this design makes possible. The account resolver
resolved a different tenant's users than the login step had, because the login passed the resource
and the resolver did not, and the symptom was a 500 in the consent screen rather than a refusal. And
the password, reset and registration doors resolved policy from the client alone, so a tenant whose
users only sign in through an upstream provider could be reached with a password through a declared
resource. Both were closed by making the resource a required argument, so an omission no longer
type-checks. If you take one engineering rule from this section, take that one: when a parameter
selects a tenant, make it impossible to call the function without it.

The last one is machine tokens. An end user consents, so any client, including one that belongs to
nobody, may ask a person for a token to a declared resource. A client credentials token asks nobody.
Until we noticed, any confidential client of any tenant, or one that registered itself, could ask a
victim tenant's token endpoint for a token with the victim's resource as audience and the victim's
issuer, and receive one. Now a machine token for a declared resource goes only to a client of the
project that declared it. There is nothing in the specification about this. There would not be; it
is a multi-tenant question.

## The scope list is a grant, not a menu

One small thing that surprised me. If your challenge carries no `scope`, the specification tells the
client to request every scope in your `scopes_supported`, and calls that intended: a general-purpose
client cannot choose sensibly among names it does not understand. So a long list in your metadata is
not a catalogue of options, it is what every agent that ever connects will be granted. Put the scope
your tools actually need in the challenge, keep `scopes_supported` to the minimum for basic use,
and ask for more with a 403 and `insufficient_scope` when a privileged tool is first called. The
client is required to treat the challenge's scope as authoritative and to accumulate scopes across
step-ups itself, which is why the authorization server can stay stateless about it. Our own
administrative MCP endpoint advertises `openid` and nothing else, because its authority comes from
the administrator's group memberships, not from scopes, and a scope the endpoint never checks is not one to publish.

## Two questions the specification leaves to you

The first is token format, and the specification is careful not to decide it. An MCP server must
reject tokens not intended for it "or otherwise verify that they are the intended recipient", which
admits both a self-contained token checked against published keys and an opaque one checked by
introspection. We default to self-contained with a fifteen-minute lifetime, because introspection
obliges your MCP server to hold credentials of its own and the ten-minute setup guide has no room
for that step. The trade is that a self-contained token is valid until it expires. If a revoked
token has to stop working within seconds rather than minutes, declare the resource opaque, give your
MCP server a client of its own, and pay for introspection on every call. Neither answer is wrong;
what is wrong is not knowing which one you chose.

The second is the confused deputy, and it is not the authorization server's to solve. An MCP server
that proxies a third-party API with one static client id, registers its own MCP clients dynamically,
and forwards codes without a consent screen of its own is exactly the setup the security guidance
walks through, attack by attack. The mitigation is per-client consent at the proxy, before the third-party flow
starts, and audience checking so that a token the proxy receives is never simply passed through.
Every piece of the specification I have described helps with that, and none of it does the work for
you.

What I do not know yet is how the trust policy for metadata documents shakes out in practice. The
specification allows an authorization server to accept any HTTPS `client_id`, allowlist domains, or
apply reputation checks, and every option is a different phishing surface, since the name on the
consent screen is whatever the document says. Open by default is what makes the ecosystem work and
allowlists are what an enterprise will want, and I suspect the answer is both, per tenant, which is
one more question the specification will keep leaving to whoever runs the server.
