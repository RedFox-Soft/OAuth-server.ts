With SCIM 2.0 the directory is the source of truth for who works here. Microsoft Entra ID, Okta or any
SCIM client creates a project's users, keeps their profiles current, puts them in groups, and
deactivates or deletes them when they leave. The same people then sign in through the same directory,
and the sign-in finds their account by the directory's own identifier rather than by email address.

Each directory is set up as one record, the **provisioning connection**. It belongs to one
project and is bound to one of that project's upstream identity providers.

<Aside
	type="note"
	title="What you need first"
>
	You need three things. First, the
	[`scim.enabled`](/docs/reference/settings/#scim.enabled) setting on. It is off
	by default because it lets a third party's system write end-user accounts. You
	can prepare connections while it is off. Second, a project with an address:
	one at a path, a subdomain or a hostname of its own, or the default project at
	the root. The administrators' project cannot be provisioned. Third, the
	directory configured as an [upstream identity
	provider](/docs/administer/federation/) of that project, because the
	connection is bound to it.
</Aside>

## Create the connection

<Steps>

1. Open the project in the console, go to its **Provisioning** tab and choose **New provisioning
   connection**. A side panel walks you through the rest.

2. **Directory.** Choose which directory provisions the project: Entra ID, Okta or another SCIM client.
   From then on the panel uses that directory's own names for each field and shows its advice. An agent
   reads the same per-directory advice with `provisioning_directory_list`. Then pick the **Sign-in provider** the
   directory's users will sign in with. One provider binds to at most one connection.

3. **Matching & trust.** Check the **correlation rule**: the ID token claim and the SCIM attribute that
   must hold the same value for a sign-in to land on a provisioned account. For Microsoft the
   recommended rule is `oid` ↔ `externalId`, because Entra's `sub` differs per application while its
   object id is stable and is what Entra sends to SCIM as `externalId`. For everything else it is
   `preferred_username` ↔ `userName`, which is what Okta sends. Then choose what to do with **Email
   addresses from the directory**. Unverified, the default, stores them unverified. Verified marks them
   verified. Choose Verified only when the directory verifies addresses itself.

4. **Safeguard.** Choose what happens when the directory removes many people at once: hold the
   connection above a limit, or apply every removal immediately. There is no default, and the panel
   cannot finish until you choose. See [The mass-deprovisioning guard](#the-mass-deprovisioning-guard).

5. **Credential.** Choose how the directory authenticates, described below for each directory.

6. **Connect.** The panel shows the **SCIM base URL**, the **Token endpoint**, the **Client id** and the
   scope to give the directory, under the names the directory uses, and says when the directory makes
   its first request.

</Steps>

Creating the connection switches its provider to **Only allow accounts that already exist**, and keeps
it there while the connection exists. Otherwise a first sign-in that created an account would race the
directory's own create and leave one person with two accounts.

At a provider bound to a connection, sign-in never looks at email addresses. The correlation rule must
name exactly one provisioned user: a sign-in with no match is refused as not provisioned, and a match already linked
to a different upstream subject is refused rather than re-linked. Upstream claims are not copied onto a
provisioned user, because the directory owns that profile.

## The address the directory calls

The SCIM base URL is the project's issuer followed by `/scim/v2`:

```
https://auth.example.com/acme/scim/v2
https://login.acme.example/scim/v2
```

It serves `/Users`, `/Groups`, `/ServiceProviderConfig`, `/Schemas` and `/ResourceTypes`. There is no
`/Bulk`, and neither Entra ID nor Okta calls it. Each connection is rate-limited on its own, 50 requests
a second by default ([`scim.rateLimit.max`](/docs/reference/settings/#scim.rateLimit.max)), rather than
per IP address, because Entra and Okta send many customers' traffic from a few IP addresses.

## Microsoft Entra ID: client credentials

Entra authenticates to the project's token endpoint as an OAuth client and presents the token it gets to
the SCIM base URL. The client is `scim-<connectionId>`, shown on the connection as **Client id**. It is
derived from the connection on every request and stored nowhere, so there is no second record to keep in
step.

On the connection's page, under **Credentials**, choose **Issue client secret…**. The secret is shown
once. In Entra's provisioning
settings, give it the SCIM base URL as the tenant URL, and the token endpoint, client id and secret for
the client-credentials grant. Entra may send the secret by Basic authentication or in the form body;
both are accepted. The token it gets carries the `scim` scope and nothing else, and works only at this
project's SCIM URL.

In Entra's **How credentials are sent**, choose Header or Body, not Both: a token request that
authenticates twice is refused (RFC 6749 §2.3). Leave the scopes empty or enter `scim`.

A client secret is a deviation from the OpenID IPSIE profile (Interoperability Profiling for Secure
Identity in the Enterprise) this server targets, which requires a signed JWT
assertion. The server accepts secrets because Entra's and Okta's OAuth modes send one. You can switch
secrets off with [`scim.secretCredentials`](/docs/reference/settings/#scim.secretCredentials). A client that can sign
uses **Issue public key…** instead, with a key set pasted in or fetched from a URL.

To rotate a secret, choose **Replace with a client secret…** and **Keep the current one working until
the directory uses the new one**. The previous secret
keeps working until the directory has used the new one and stopped using the old one for an hour, and
never longer than 24 hours, so synchronisation does not stop while you paste the new value. **Retire
previous now** ends the previous secret early, together with every token it obtained. If a secret leaked, replace it
with **Stop the current one now** instead: it stops at once. Issuing a public key, or switching between
a secret and a key, replaces the previous credential at once. An agent issues and replaces credentials
with `provisioning_credential_issue` (`overlap: false` stops the previous value at once), retires the
previous one early with `provisioning_credential_retire`, and removes one with
`provisioning_credential_revoke`.

## Okta: a client secret, or a static token in header mode

Okta's SCIM settings offer **OAuth2** with the Client Credentials grant type; use it where your Okta
organisation offers it, with a client secret issued here, as for Entra. Where it does not,
Okta gets a static token. Under **Credentials**, choose **Issue static token…** and its lifetime, 90
days or one year (`lifetimeDays` over the API). The token begins with `scimst_`, is shown once, and is stored only as a digest. In
Okta's SCIM settings, choose **HTTP Header** authentication and paste the token as it is. Okta sends it
without a `Bearer` prefix, and the `scimst_` prefix is what lets this server recognise it.

A static token expires (RFC 7644 §7.4); the connection page and the project's overview warn 14 days
before. To rotate, choose **Replace static token…**: as with a secret, the previous token keeps working
until Okta has moved to the new one, at most 24 hours, so there is no gap to schedule around.
**Revoke…** on the static token removes it without issuing another. Tokens issued before 0.11.0 were
given an expiry by the upgrade: a year from their issue, and never sooner than 90 days from the
upgrade. Static tokens are another deviation
from the profile, switched by [`scim.staticTokens`](/docs/reference/settings/#scim.staticTokens).

## Users and groups

`/Users` creates, reads, filters, replaces, patches and deletes the project's end users. `userName` is
unique in the project regardless of letter case; `externalId` is unique within the connection.
Deactivating a user through SCIM ends their access at once, exactly as an administrator's deactivation
does: see [End a user's access](/docs/administer/ending-access/).

`/Groups` manages the project's groups that the connection owns, and their members. A group PATCH answers
`204`, which is what Entra and Okta expect. Large groups are filled by PATCH batches of members
rather than in the create. Relying parties read the result in the [`groups` claim](/docs/administer/groups/).

Both directories send requests a strict SCIM server would refuse: a PATCH with no `path`, operations in
capitals, booleans as the string `"False"`, attributes the schema does not declare, a `password` on
every create, Entra's `manager` as a bare id. While [`scim.strict`](/docs/reference/settings/#scim.strict)
is off, the default, the server accepts them. Turn it on only if you are certifying against the profiles rather than
connecting Entra or Okta; `/ServiceProviderConfig` then declares the interoperability profile conformant.
It is one switch rather than one per tolerance because no partial combination is conformant.

## Provisioned users are read-only here

A user or group a connection created belongs to that connection. In the console its **Managed by**
column names the connection, and an edit, password reset or deletion by an administrator is refused
with `409`. A connection sees only its own users and groups. The exceptions are deliberate: an
administrator can still clear a user's authenticator, which is account recovery rather than a profile
edit, and can lock the account, a control the directory cannot reach or undo.

An existing local user can be handed to a connection, with the names the directory knows them by.
An administrator-kept group can be handed over the same way, once every member is someone that
connection manages.

## The mass-deprovisioning guard

A wrong scoping rule in the directory, or a stolen credential, can deactivate a whole project in minutes,
and deactivation here ends sessions, grants and consents. Each connection can carry a threshold:
**at most** a number of deprovisionings, from 1 to 100,000, within a window of 5 minutes to 7 days.
A deactivation and a deletion of an existing user each count.

The first deprovisioning beyond the threshold **holds** the connection. While it is held, every
deactivation and deletion is refused with `429` and `Retry-After: 300` and changes nothing.
Creates, updates and group changes keep flowing. The project's administrators get one email, which links
to the connection's page. Both directories retry a `429` by themselves, so nothing is lost: the refused
requests land once the hold is released.

Each refusal is recorded per person: who, which operation, when first and last, and how many attempts.
The connection's page lists them, and an agent reads them with `provisioning_hold_get`. A held
connection also shows as **On hold** on the **Projects** list, and `provisioning_hold_list` lists every
held connection the caller can see.

Only an explicit release ends a hold: **Release hold…** on the connection's page, or
`provisioning_connection_release` for an agent, which is a high-consequence tool that asks for
confirmation. No edit ends one, and removing the threshold of a held connection is refused. Look at
whom the directory was trying to remove before releasing; the refused deprovisionings arrive as soon as
you release it. The release clears the per-person records, and its audit entry keeps their count.

The guard is off until you set a threshold, and setting one departs from the IPSIE profile, which wants
deprovisioning to end access promptly: a leaver caught by a hold keeps access until the release. That
trade is yours to make per connection.

## Deleting a connection

A connection that still manages users or owns groups cannot be deleted, because deleting people must
never be a side effect of deleting configuration. Disable it instead, or have the directory remove what
it provisioned first.

## What has and has not been tested

Microsoft's SCIM validator and Okta's SCIM 2.0 Spec Test both pass against the conformance deployment,
with users and groups. Okta's CRUD test, which needs an Okta organisation with the integration
installed, has not been run, and certification has not been applied for. The detail, including the one
validator failure attributed to the validator itself, is in
[CONFORMANCE.md](https://github.com/RedFox-Soft/OAuth-server.ts/blob/main/CONFORMANCE.md#scim-provisioning-ipsie-al-scim-profile).
