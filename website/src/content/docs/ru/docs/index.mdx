FoxAuth построен на **OAuth-server.ts**. Это сервер авторизации OAuth 2.1 и OpenID Connect с доступным
исходным кодом (source-available). Его можно развернуть у себя или бесплатно использовать в FoxAuth Cloud. Эта документация охватывает три
задачи: запустить сервер, подключить к нему приложение и сопровождать его, когда от него начинают
зависеть реальные пользователи. Выберите ту, которой заняты сейчас.

## Запуск сервера {#getting-it-running}

Начните с раздела [Запуск с Docker Compose](/ru/docs/get-started/docker-compose/). Одна команда
запускает MongoDB, подготавливает схему и поднимает сервер авторизации. Пожалуй, так быстрее всего
увидеть работающий экземпляр. Если вы предпочитаете работать с исходным кодом, раздел [Запуск из
исходного кода](/ru/docs/get-started/from-source/) описывает, как клонировать репозиторий и запустить
сервер на Bun.

В обоих случаях дальше откройте раздел [Создание первого администратора](/ru/docs/get-started/first-admin/): в
новой базе данных нет ни одной учётной записи, и первая создаётся на одноразовом экране настройки.
Первым делом включите там второй фактор.

Чтобы не запускать сервер самому, [создайте бесплатную учётную запись в FoxAuth Cloud](https://auth.foxauth.dev/admin/signup)
(это наш экземпляр на `auth.foxauth.dev`). Вы получите личную команду и до двух проектов на
[тарифе Free](/docs/administer/plans/#the-free-plan). Страницы раздела «Начало работы» рассчитаны на сервер по
адресу `http://localhost:3000`: в облаке подставляйте вместо него адрес издателя (issuer) своего проекта, он показан на вкладке
**Overview**. На тарифе Free вход через внешних провайдеров возможен только через Google, Microsoft, Apple и GitHub.

## Подключение приложения {#connecting-an-application}

Приложение взаимодействует с сервером как **OAuth-клиент**, и клиент должен существовать до того, как
сможет запросить токен. Раздел [Регистрация первого клиента](/ru/docs/get-started/first-client/)
разбирает то, на чём чаще всего спотыкаются: разницу между публичным и конфиденциальным клиентом,
почему redirect URI сравниваются точно и никогда по шаблону и из какого проекта клиент впускает
людей.

Затем [Получение первого токена](/ru/docs/get-started/first-token/) проводит через Authorization Code
flow с PKCE (Proof Key for Code Exchange) от начала до конца с помощью `curl`: от code challenge до декодированного ID-токена и
вызова UserInfo. По умолчанию PKCE обязателен для каждого клиента, а не только для публичных. Этого требует OAuth 2.1.
По нашему опыту, именно это требование чаще всего удивляет тех, кто переходит с сервера OAuth 2.0.

Если вы подключаете **MCP-сервер**, то он не OAuth-клиент, а защищённый ресурс, и схема
отличается настолько, что ей посвящена отдельная страница: [Защита MCP-сервера с помощью
OAuth](/ru/docs/get-started/protect-your-mcp-server/). Там MCP-сервер объявляется на этом сервере,
публикуются две вещи, которые обязан публиковать любой MCP-сервер, проверяется токен и показаны как
отказ, так и успешный запрос.

## Работа в продакшене {#running-it-in-production}

Раздел [Развёртывание](/ru/docs/deploy/fly/) охватывает три платформы:
[Fly.io](/ru/docs/deploy/fly/), [Kubernetes](/ru/docs/deploy/kubernetes/), [Docker
Compose](/ru/docs/deploy/docker-compose/) на одном хосте. В качестве базы данных можно выбрать
[MongoDB](/ru/docs/deploy/mongodb-atlas/) или [PostgreSQL](/ru/docs/deploy/postgresql/), и выбор
определяет заданная вами строка подключения. Что бы вы ни выбрали, прочитайте раздел [За обратным
прокси](/ru/docs/deploy/reverse-proxy/). Адрес issuer должен начинаться с `https://` и
совпадать с тем, что настроено в клиентах. Обычно токены проходят проверку локально и не проходят в
продакшене из-за прокси, который переписывает заголовки, хотя его об этом не просили.

Прежде чем переходить на другую версию, прочитайте раздел [Обновление](/ru/docs/deploy/upgrade/).
Начиная с 1.0.0 HTTP-интерфейс и admin API меняются несовместимо только в мажорном релизе; что
изменилось, сказано в changelog. После обновления заново запустите скрипт
настройки, чтобы появились новые коллекции и индексы, а затем выполните `bun run db:migrate`: эта
команда применяет всё, что релиз должен перестроить.

## Администрирование проектов, когда пользователи уже входят {#running-it-for-real-users}

Когда через сервер начинают входить люди, основная работа переходит в консоль. [Подключение внешнего
провайдера идентификации](/ru/docs/administer/federation/) позволяет пользователям проекта входить через
Google, Microsoft, Apple, GitHub или любой провайдер OpenID и определяет, какие учётные записи такой вход
может создавать или связывать. Когда провайдер подключён, [Провижининг пользователей из Entra ID или
Okta](/ru/docs/administer/scim/) передаёт пользователей и группы проекта под управление каталога по SCIM,
а [Выход через внешних провайдеров](/ru/docs/administer/upstream-logout/) позволяет выходу у внешнего
провайдера завершать сессии пользователя на этом сервере.

[Команды и владение проектами](/ru/docs/administer/teams/) описывает команды администраторов,
которым принадлежат проекты, и перенос проекта из одной команды в другую. [Адреса
проектов](/ru/docs/administer/project-addresses/) сравнивает три вида адреса проекта: путь, поддомен и
собственное имя хоста. Там же сказано, что нужно оператору для поддоменов. [Группы и claim
groups](/ru/docs/administer/groups/) описывает группы конечных пользователей, которые relying party
читает вместо ролей. [Прекращение доступа пользователя](/ru/docs/administer/ending-access/)
сравнивает деактивацию, блокировку, выход на всех устройствах и удаление и называет единственный
токен, который ни один из этих способов не может отозвать. [Ротация ключей
подписи](/ru/docs/administer/signing-keys/) показывает, как одним действием и без перезапуска
ротировать ключи экземпляра и каждого проекта и как сразу отозвать скомпрометированный ключ. [Тарифы и
ограничения Free](/ru/docs/administer/plans/) нужны публичному экземпляру, где администратором может
зарегистрироваться кто угодно. Тариф ограничивает, что может создавать каждая команда, и приостанавливает
новые регистрации, когда проект достигает лимита активных пользователей в месяц.

## Стоит ли доверять этому серверу {#deciding-whether-to-trust-it}

Сервер авторизации служит входной дверью ко всему, что за ним стоит. Прежде чем ставить его перед
реальными пользователями, вы вправе спросить, от чего он защищает и откуда это известно. [Модель
угроз](/ru/docs/security/threat-model/) отвечает на первый вопрос: активы, атакующие, а для каждой угрозы
механизм защиты в коде и тест, который его проверяет, а также ограничения, актуальные на сегодня.
[Гарантии безопасности](/ru/docs/security/assurance/) отвечают на второй: сканирование, которое
запускается при каждом push и каждую неделю, где публикуется каждый результат и что ещё не сделано. Как
сообщить об уязвимости, описано в [политике безопасности](/security/).

## Справочник, сгенерированный из исходного кода {#looking-something-up}

Раздел Reference генерируется из исходного кода самого сервера при каждой сборке, поэтому описывает тот
релиз, из которого собран сайт; ничего в нём не поддерживается вручную:

- **[Настройки](/docs/reference/settings/)**: каждый флаг и параметр уровня сервера, что он делает и
  требует ли его изменение перезапуска.
- **[Эндпоинты](/docs/reference/endpoints/)**: каждый маршрут, который обслуживает сервер, какой флаг
  им управляет, а также его класс CORS и класс ограничения частоты запросов.
- **[Admin API](/docs/reference/admin-api/)**: API управления, на котором работает консоль.
- **[MCP-инструменты](/docs/reference/mcp-tools/)**: операции, которые может выполнять ИИ-агент.
  Это намеренно составленный allow-list, более узкий, чем весь административный интерфейс.
- **[Точки расширения (addon seams)](/docs/reference/addon-seams/)**: именованные функции, которые вы
  заменяете своими вместо того, чтобы делать форк.
- **[Переменные окружения](/docs/reference/environment/)**: что должно быть задано, чтобы сервер
  запустился.

## Чего сервер не поддерживает {#what-this-server-is-not}

Сервер поддерживает только OAuth 2.1 и OpenID Connect. Поддержки SAML нет и не планируется.
Типы грантов Implicit и Resource Owner Password Credentials не реализованы, потому что OAuth 2.1 их убирает.
Если приложение зависит от любого из них, его придётся изменить, прежде чем оно сможет работать с этим
сервером.

Если вы ещё решаете, стоит ли вообще его запускать, [сравнения](/ru/compare/) ставят его рядом с
серверами, с которыми его обычно сопоставляют команды, и указывают дату проверки каждого утверждения.
