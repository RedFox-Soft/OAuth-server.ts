服务器自己管理自己。没有需要去日志里查找的预置密码，也没有 `create-admin` 命令。第一个管理员在浏览器中创建，而且只创建一次。

<Aside type="note" title="在 FoxAuth Cloud 上">

FoxAuth Cloud 没有初始设置页面。打开 `https://auth.foxauth.dev/admin/signup`，创建账户，然后点击邮件中的链接确认邮箱地址。你的账户会得到一个个人团队（只有你一个成员的团队），但没有项目：项目由你自己创建。实例设置、邮件和 **Administrators** 页面由我们管理，因此本页其余内容讲的是运行你自己的服务器。

</Aside>

<Steps>

1. 在一个刚完成初始化的部署上打开 `/admin`，例如 `http://localhost:3000/admin`。

2. **Create the first super admin** 页面会要求输入一个电子邮件地址和一个至少十二个字符的密码。该账户会进入保留的「Administrators」项目，成为 **Super administrators**（其成员管理整个实例的团队）的成员，并且像其他任何管理员一样获得一个个人团队。

3. 提交，然后用这些凭据登录。

</Steps>

一旦 Super administrators 有了一个活跃成员，设置路由就会关闭，此后一律返回 `409 already_initialized`。`/admin` 变成登录页面。

后续的管理员在控制台的 **Administrators** 页面上通过 **New administrator** 创建，同样需要一个电子邮件地址和一个至少十二个字符的密码。超级管理员还可以在该页面的 **Sign-in** 标签页上开放注册，让人们自行注册，或者在 **Identity providers** 下连接你所在组织的身份提供商。注册只能与电子邮件验证在同一次更改中一起开启。如果不要求验证，任何人都能用同事的地址注册一个管理员账户。

无论通过哪种方式加入，新管理员都不会是超级管理员。这一身份要由超级管理员在账户菜单中通过 **Make super administrator…** 单独授予。（常规团队的成员资格是通过电子邮件邀请提供的。）

如果你在一个本应已有管理员的部署上看到了设置页面，请调查原因：这意味着此服务器读取的账户集合里一个账户都没有。

<Aside type="caution">

`/admin` 是一个向互联网开放的登录页面。首次运行流程的任何环节都没有经过身份验证，也不可能经过，因为此时还不存在任何账户。所以部署一启动，就立即创建第一个管理员，不要让一个可访问却尚未初始化的实例闲置在那里。

</Aside>

## 管理员通过此服务器自己的签发者登录 {#administrators-sign-in-through-this-servers-own-issuer}

登录控制台是一次 OpenID Connect 授权码流程，针对的正是控制台所管理的这台服务器，使用的是 `db:setup` 预置的第一方 `admin-panel` 客户端。没有第二套密码存储，也没有仅供管理员使用的凭据路径：管理员就是保留的管理员项目中的一个最终用户，管理 API 允许他们做什么，取决于他们所属的团队。

由此产生两个后果，两者在实践中都会遇到：

- 预置客户端的重定向 URI 是 `$ISSUER/admin/callback`，只在该客户端首次插入时写入一次。如果在预置之后修改了 `ISSUER`，登录会重定向到一个该客户端并未登记的 URI 并因此失败；重新运行 `db:setup` 也不会更新这个重定向 URI。处理方法参见 [Compose 指南中的警告](/zh-cn/docs/get-started/docker-compose/)。
- 没有种子数据就无法访问控制台。如果 `db:setup` 从未运行过，`/admin/login` 会带着一个没有任何客户端匹配的 `client_id` 重定向到 `/auth`。

## 开启第二因素认证 {#turn-on-the-second-factor}

管理员项目是一扇暴露在公共互联网上、只靠密码把守的门，所以我们的建议是：在做其他任何事之前，先要求它使用身份验证器应用。在控制台中进入 **Administrators** 页面（仅限超级管理员），打开 **Sign-in** 标签页，开启 **Require an authenticator app for password sign-in** 并保存。控制台会先显示还有多少管理员没有绑定身份验证器，并请你确认。

之后登录除了密码，还需要一个六位数的验证码。开启这项要求不会把任何人锁在门外：尚未绑定身份验证器的管理员会在下次登录时完成绑定。这也包括使用 `db:setup` 预置的保留 `admin-mcp` 客户端登录的智能体，因为它走的是同一扇门。通过身份提供商登录的管理员则使用该提供商的第二因素；这项要求只适用于密码登录。

真正让这扇门变得坚固的是第二因素，而不是登录节流（对失败密码尝试的限制）。节流按项目和电子邮件地址统计失败的密码尝试，达到上限的地址会在一段时间内被拒绝。通常每一次后续锁定都会比上一次更长。按照设计，要求一次性验证码的项目无论被触发多少次，都停留在第一次锁定的时长：在那里猜中密码也无法让任何人登录。管理员也没有自助重置密码的途径来摆脱锁定。节流本身的设置是[设置参考](/docs/reference/settings/#loginThrottle.failureCap)中的 `loginThrottle.failureCap`、`loginThrottle.windowSeconds` 和 `loginThrottle.windowCeilingSeconds`。

## 设置邮件 {#set-up-mail}

服务器通过邮件来验证地址、重置密码和邀请他人。在设置好邮件之前，这些功能都无法使用，管理员注册也无法开放。

1. 打开 **Settings → Integrations**，填写 **Email (SMTP)** 卡片：邮件服务商的主机和端口、登录名和密码，以及发件人的名称和地址。许多服务商只接受与登录名或其别名一致的发件人地址。
2. 点击 **Save**，再点击 **Send test email**。邮件会发送到你自己的地址。
3. 如果邮件服务器拒绝，卡片会显示它的回复，例如 `535 Authentication failed`。如果服务器接受了邮件但没有收到，请查看垃圾邮件，并检查发件人域名的 SPF、DKIM 和 DMARC 记录。

智能体用 `smtp_settings_update` 和 `smtp_settings_test` 完成同样的操作。

## 管理员能触及什么 {#what-an-administrator-can-reach}

控制台的超级管理员功能覆盖实例本身：服务器设置、签名密钥、SMTP、管理员账户和故障存储。超级管理员的身份，就是保留的 **Super administrators** 团队的成员资格。这一成员资格的授予和撤回各自是独立的操作：**Administrators** 页面上的 **Make super administrator…** 和 **Withdraw super administration…**，对智能体而言则是 `admin_super_grant` 和 `admin_super_withdraw`。最后一个活跃成员既不能被撤回，也不能被停用。

其他任何管理员都可以创建项目、项目中的应用和 API，以及团队。他们可以通过电子邮件邀请他人加入自己的常规团队，并读取自己所属团队的审计日志和 **Usage** 页面。所有权按团队划分：属于某个项目的所属团队，就是获得其访问权限的方式。详见[团队与项目所有权](/zh-cn/docs/administer/teams/)。

每一个改变状态的操作，无论来自控制台还是智能体，都会在变更发生之前写入只追加的审计日志，记录操作者、操作和目标。该存储不提供任何更新或删除接口。

如果你发现的是安全问题而非配置问题，我们的漏洞披露政策和联系方式见[安全页面](/security/)。
