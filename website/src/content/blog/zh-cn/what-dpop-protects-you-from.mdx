令牌出现在一份崩溃报告里。

有个移动客户端在对接我当时运营的一个 API。它用的 HTTP 库在遇到未处理的异常时，会把失败的请求序列化，发送给第三方崩溃收集服务——连请求头一起。于是在那家供应商仪表盘的某个角落，躺着一条 `Authorization: Bearer eyJhbGci...`，它还有十四分钟有效期，对方轮值支持团队里的每个人都能读到。据我所知，没有人拿它做过什么。但假如有人这么做了，协议里没有任何东西能阻止他们。

这不是谁的实现有 bug。RFC 6750 在这个术语的定义里就写明了：任何持有 bearer 令牌的一方都可以使用它。资源服务器会检查签名、过期时间、受众和 scope（作用域）。但它从不问那天下午唯一要紧的那个问题：调用方是不是令牌所颁发给的那一方？它没法问，因为请求里没有任何可供询问的东西。

DPoP（RFC 9449）在请求里放进了可供询问的东西。我想把它能换来什么、换不来什么说准确，因为我见过它被当作「阻止令牌盗用」来推销。它做的事情更窄，也更有用。

## 客户端签的是什么 {#what-the-client-signs}

客户端在申请令牌之前先生成一个密钥对，并自己保管私钥。每个出示该令牌的请求，都同时出示一个小小的已签名 JWT，即证明（proof）：它的 header 携带公钥，payload 描述它所属的那个请求。解码之后，一次 userinfo 调用的证明长这样：

```json
{
  "typ": "dpop+jwt",
  "alg": "ES256",
  "jwk": { "kty": "EC", "crv": "P-256", "x": "l8tFrhx-34tV3hRICRDY9zCkDlpBhF42UQUfWVAWBFs", "y": "9VE4jf_Ok_o64zbTTlcuNJajHmt6v9TDVrU0CdvGRDA" }
}
{
  "jti": "e1j3V_bKic8-LAEB",
  "htm": "GET",
  "htu": "https://auth.example.com/userinfo",
  "iat": 1758196200,
  "ath": "fUHyO2r2Z3DZ53EsNrWBb0xWXoaNy59IiKCAqksmQEo",
  "nonce": "eyJ7S_zG8SxF0SbEjb-5aYW7Xbt9Jd_kKdIaI4BbX2o"
}
```

每个声明（claim）都堵住一个漏洞，否则某种特定的重放就会从那里钻过去；下图标出了哪个声明堵住哪个漏洞。看那些箭头：每一支都从证明出发，落在服务器可以不依赖客户端、独立检查的某样东西上。

那支强调色的箭头是整个方案的支点：它就是发送方约束（sender-constraint），即把令牌绑定到一把密钥上，而发送方必须证明自己持有这把密钥。访问令牌携带一个确认声明 `cnf.jkt`，即签署证明的那把公钥的 RFC 7638 指纹。一个从未和客户端打过交道的资源服务器，仅凭令牌本身就能得知它属于哪把密钥，再检查这份证明是否由那把密钥签署。`ath` 防止有人把一份证明从一个令牌上摘下来，挂到另一个碰巧绑定了同一把密钥的令牌上。`htm` 和 `htu` 防止为某个端点制作的证明被重放到另一个端点。`jti` 让服务器能发现同一份证明出现了两次。`nonce` 和 `iat` 都关乎新鲜度，它们单独占一节，因为大部分运维上的痛苦都在那里。

下面是线上的全貌，从授权码交换开始。和普通的 PKCE 交换相比，唯一可见的新增内容是请求上的 `DPoP` 头和响应里的 `token_type`：

```http
POST /token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7Imt0eSI6IkVDIi...

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcb
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk&client_id=spa-7f3a
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCIsImtpZCI6IjIwMjYtMDkifQ...",
  "token_type": "DPoP",
  "expires_in": 900,
  "scope": "openid orders:read",
  "refresh_token": "Ql3oQ4fq8NWY0m9tHqqvqA1H7ArTn0O1x1PbUdECfxa"
}
```

`token_type: DPoP` 是服务器在告诉客户端：从现在起，`Authorization` 里该用哪种方案。客户端发送 `Authorization: DPoP <token>` 而不是 `Bearer`；服务器若在 `Bearer` 方案下收到一个绑定了 DPoP 的令牌，应当拒绝它，因为一个不知道自己持有绑定令牌的客户端，同样也不会发送证明。如果访问令牌是不透明令牌，绑定信息以 `cnf` 成员的形式出现在内省响应里。如果它是 JWT（这里正是如此），同样的成员就在它的 payload 中：

```json
{
  "iss": "https://auth.example.com",
  "sub": "248289761001",
  "aud": "https://api.example.com",
  "client_id": "spa-7f3a",
  "exp": 1758197100,
  "scope": "openid orders:read",
  "cnf": { "jkt": "0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I" }
}
```

于是整个流程就是：授权服务器上的两步，加上资源服务器上的一个验证环节，而值得盯着细看的，正是这个验证环节。

现在把那份崩溃报告放进来走一遍。供应商的支持工程师拿到了访问令牌。他们没有 K，所以无法用它签署证明。用任何其他密钥签署的证明，都会在第 4 步比对指纹的那一行失败，令牌单独拿着一文不值。再假设他们截获的是整个请求，令牌和证明一起。这份证明只对一个方法、一个 URL、一个令牌有效，时效要么是 `iat` 的五分钟，要么是一个 nonce；如果资源服务器维护着重放存储，它就恰好只能用一次。攻击者从持有一个十四分钟有效的密码，变成了持有一个也许能、也许不能重复发送的单个请求。

## 被过度宣传的部分 {#the-part-that-gets-oversold}

这是实实在在的改进，同时也就是改进的全部。DPoP 防范的是令牌在签发之后、在客户端之外泄露：崩溃报告、代理日志、`Referer` 头、读取存储的浏览器扩展、配置错误的缓存。在所有这些情形里，攻击者最终拿到的是令牌，而不是密钥。

对于在密钥所在之处运行代码的攻击者，它毫无作用。一个把密钥存在 IndexedDB 里的单页应用，一旦遭遇跨站脚本攻击，攻击者根本不需要外泄任何东西。注入的脚本直接用真正的密钥签署证明，以真实用户的身份、从真实的页面调用 API，第 4 步的每项检查都会通过——它们本就应该通过。把令牌绑定到攻击者同样能使用的密钥上，什么也保护不了。我在不止一次设计评审中看到，有人把「我们用了 DPoP」当作「前端被攻破会怎样」的答案，而它根本不是那个问题的答案。它阻止的是被盗令牌在别处被重放。它阻止不了持有密钥的那个地方被攻破。

它也替代不了那些乏味的控制措施。一个有效期四小时、没有受众限制的 DPoP 绑定令牌，落到攻破客户端的人手里，依然是一个四小时有效、任意受众的令牌。限制这种爆炸半径的是短有效期、受众限制和刷新令牌轮换；DPoP 是与它们组合使用，而不是取代其中任何一项。

## nonce，以及真正的敌人为什么是时钟 {#the-nonce-and-why-the-real-enemy-is-clocks}

如果放任不管，证明的新鲜度取决于 `iat`，也就是取决于客户端的时钟和服务器的时钟是否一致。我们的服务器接受与自身时间相差 300 秒以内的 `iat`，而 RFC 有意把这个窗口交给服务器决定。一部时钟偏差六分钟的手机，每个请求都会以 `invalid_dpop_proof` 失败，而这个错误里没有任何地方说「你的时钟不对」。它说的是证明有问题。总会有人为此耗掉一个下午，我就当过那个人。

服务器 nonce（RFC 9449 §8 和 §9）用服务器的时钟取代客户端的时钟。服务器下发一个不透明值，客户端把它作为 `nonce` 放进下一份证明，只要这个 nonce 是服务器最近签发的，证明就会被接受。新鲜度现在来自 nonce，`iat` 退居参考。代价是客户端首次接触时没有 nonce，所以第一个请求按设计必然失败，而这次失败必须把修复方法带回来：

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: DPoP error="use_dpop_nonce", error_description="nonce is required in the DPoP proof", algs="ES256 PS256"
DPoP-Nonce: eyJ7S_zG8SxF0SbEjb-5aYW7Xbt9Jd_kKdIaI4BbX2o
```

客户端读取 `DPoP-Nonce`，用它签署一份新证明，然后重试。之后的每个响应都可能携带一个新的 `DPoP-Nonce`，客户端把它换进下一个请求。因此，一个持续繁忙的客户端再也不会看到 401，而一个空闲的客户端在几分钟后会再看到一次。这就是下图所示的往返，客户端库必须把它实现成一个循环，而不是当作错误来处理。

这次交换里有两件事花掉了我们实实在在的时间，而且都与密码学无关。第一件是状态码。RFC 9449 要求授权服务器把错误的证明报告为 400、错误放在响应体中，和令牌端点的其他所有错误一样。资源服务器则报告为 401、错误放在 `WWW-Authenticate` 中，和 RFC 6750 的做法一样。同一类错误，两种状态码，取决于端点扮演的是哪个角色。我们曾经让两个受保护资源各自在 catch 块里自行纠正状态码，后来才把这个决定移进共享的错误处理器、按路由区分，这样新增第三个资源时就不可能绕开它。

第二件是 CORS。除非服务器在 `Access-Control-Expose-Headers` 中列出 `WWW-Authenticate` 和 `DPoP-Nonce`，否则浏览器无法从跨源响应中读取它们；没有它们，单页应用看到的只是一个不透明的 401，永远无法完成重试。规范只是顺带提了一句。可这恰恰决定了 DPoP 在浏览器里能用还是不能用。

nonce 背后藏着一个设计问题，我觉得它比规范所呈现的更有意思：服务器怎么知道哪些 nonce 是它最近签发的？显而易见的答案是存下来，而这是个糟糕的答案，因为每个响应都会签发 nonce，于是每次 API 调用在返回之前都得先写一次存储。我们改为推导。某一分钟的 nonce，是以分钟序号为 salt、对服务器密钥做 HKDF 得到的值；只要证明里的 nonce 与当前前后共五分钟中的任意一个匹配，就接受它：

```ts
const STEP = 60;

function nonceFor(secret: Uint8Array, step: number): string {
	const salt = new Uint8Array(8);
	new DataView(salt.buffer).setBigUint64(0, BigInt(step));
	return base64url(hkdfSync('sha256', secret, salt, '', 32));
}

export function nextNonce(secret: Uint8Array): string {
	return nonceFor(secret, Math.floor(Date.now() / 1000 / STEP) + 1);
}

export function acceptsNonce(secret: Uint8Array, nonce: string): boolean {
	const now = Math.floor(Date.now() / 1000 / STEP);
	let matched = 0;
	for (const offset of [-2, -1, 0, 1, 2]) {
		matched |= Number(constantTimeEqual(nonceFor(secret, now + offset), nonce));
	}
	return matched === 1;
}
```

这里面有三个选择是刻意的。下发的 nonce 是下一分钟的，而不是当前这一分钟的，因此在某一分钟快结束时拿到它的客户端，在它滑出窗口之前仍有三四分钟可用。比较会针对全部五个候选值进行，并把结果合并起来，而不是一匹配上就返回，因此所花的时间不会透露究竟是哪一分钟匹配上了。而且什么都不存储，这意味着任何持有相同密钥的副本都会接受其他副本签发的 nonce，重启也不会遗忘任何东西，因为本来就没有东西可遗忘。你放弃的是撤销能力：推导出来的 nonce 无法提前收回，而且它不区分客户端。这没问题，因为 nonce 是新鲜度令牌，不是一次性令牌。一次性这一性质来自 `jti`，把两者混为一谈，正是人们误以为 nonce 能提供重放保护的原因。它不能。

## 重放检测是热路径上的一个数据库 {#replay-detection-is-a-database-on-your-hot-path}

`jti` 唯一性意味着要按客户端记住你接受过的每一个证明标识符，记住的时长等于证明仍可能被接受的时长：五分钟；如果证明标注的时间比服务器时钟超前，最长可达十分钟。这意味着每次经过认证的 API 调用都有一次写入，之前还有一次读取。对于一个自动扩缩、自身没有任何状态的函数式资源服务器来说，这是 DPoP 之前不存在的新依赖。人们第一次注意到它，通常是在重放存储触发告警、把他们叫起来的时候。

诱惑在于把它关掉，在这里我想坦白我们做过的一个决定。我们的服务器有一个禁用重放检测的开关。它是启动配置，并且刻意没有出现在管理控制台和管理 API 中。它的存在，是为了一个故意重放同一份证明的一致性测试套件，以及一个在排查问题时重复发送请求的人；这两者都不属于管理工作。一个在发现文档仍然宣告该功能的同时、移除了一项安全属性的开关，恰恰是那种会在凌晨两点的事故中被拨动、然后再也没被拨回来的东西，而管理控制台正是凌晨两点发生的地方。所以它不在那里。

没有它，你真正失去的东西比「DPoP 失效了」要窄。截获了完整请求（令牌加证明）的攻击者，可以重放那个一模一样的请求，同样的方法和 URL，直到证明的 nonce 或 `iat` 过期。把一个 `GET /orders` 重放五分钟，是真实的泄露，但不是灾难；把一个 `POST /transfers` 重放五分钟，就是另一回事了。如果你的 API 是幂等且以读为主的，你完全可以合理地认定这个存储不值得。我不会默认做出这个决定，也不会让它能在网页上来回切换。

## DPoP 最能发挥作用的地方不是访问令牌 {#where-dpop-does-its-best-work-is-not-the-access-token}

规范里有一条很容易一扫而过的条款。对于公共客户端，也就是无法在令牌端点认证自身的客户端，刷新令牌同样绑定到密钥。对于机密客户端则不然，因为机密客户端的刷新令牌已经绑定到服务器每次使用时都会检查的客户端凭据上。我们的实现只是一个条件判断：当客户端的认证方法是 `none` 时，刷新令牌继承访问令牌的 `jkt`。

我认为，这条条款是在浏览器中使用 DPoP 最有力的论据，比任何关于访问令牌的论点都更有力。在单页应用里，访问令牌存活十五分钟，刷新令牌存活数天，而它就存放在浏览器存储里——这恰恰是拿到泄露的浏览器配置文件备份或使用共享机器的攻击者最可能找到它的地方。在 DPoP 之前，从浏览器中窃取的刷新令牌，在轮换允许它存活的期间里，就是这个账户的钥匙。有了 DPoP 和不可导出的 WebCrypto 密钥，被盗的刷新令牌只是一个无法兑换的字符串，因为兑换本身就需要一份由从未离开该源的密钥签署的证明。轮换依然重要，但它现在拦截的是一个已经被挡住的攻击者，而不是一个已经登堂入室的攻击者。

同样的思路还能再往前延伸一步，即 `dpop_jkt`：这是一个授权请求参数，在授权码签发之前就把它绑定到密钥上。这样，在重定向和交换之间被截获的授权码，就无法用另一把密钥兑换。PKCE 已经覆盖了这片领域的大部分，而且当证明随推送授权请求一同到达时，我们的服务器会自动填入 `dpop_jkt`，所以实际上它没有任何成本。它不是开启 DPoP 的理由，也不是关闭 DPoP 的理由。

## 我会在哪里用它，又会在哪里不用 {#where-i-would-use-it-and-where-i-would-not}

成本有三项，而签名不在其中。客户端需要一把密钥、一个存放它的地方，以及每个请求上的一份证明。在浏览器里，这意味着 IndexedDB 中一个不可导出的 `CryptoKey`；在原生应用里，这意味着平台密钥库；而一把可导出的密钥，会悄悄把你付出代价换来的大部分东西又还回去。客户端需要把 `use_dpop_nonce` 当作重试而不是失败，服务器则需要向跨源调用方暴露两个响应头，否则重试永远无法发生。还有，必须有人负责一个五分钟过期的重放存储，或者为不建它的那个决定负责。

与之相对，在这些情形里 DPoP 物有所值：令牌途经你无法控制的基础设施；公共客户端持有长期有效的刷新令牌；或者单个令牌泄露的爆炸半径大到「谁捡到都能用十四分钟」不是一句你能在评审中大声说出口的话。对于一个第一方的、服务端的机密客户端，它通过 TLS 与自己的 API 通信，使用五分钟有效期、受众严格限定的令牌，我不会费这个事；mTLS 绑定令牌或者普通的短期 bearer 令牌，能以更少的客户端代码换来同样的东西。

我没有答案的问题，是浏览器接下来会怎么做。Device Bound Session Credentials 原是 Chrome 的提案，如今已是一份 IETF 草案，它试图为 cookie 提供同样的属性。在它那里，密钥由浏览器而不是页面持有，而这恰恰是 DPoP 无法跨越的边界。如果它落地，并发展出面向 API 令牌的方案，大量客户端 DPoP 代码就会变成平台替你完成的事。如果它停留在 cookie 功能的层面，DPoP 就仍是浏览器客户端在不使用客户端证书的情况下唯一可用的发送方约束机制。我会按第二种情况去构建，并乐于看到第一种情况发生。

如果你想在一个运行中的服务器里看看它的样子：FoxAuth 先在服务器范围开启 DPoP，再通过 `dpop_bound_access_tokens` 客户端属性按客户端开启。nonce 要求是一项设置，重放开关就是上文所说的那个，刻意不出现在控制台中。[设置参考](/docs/reference/settings/)列出了这些选项，[端点参考](/docs/reference/endpoints/)说明了哪些端点接受证明，[威胁模型](/zh-cn/docs/security/threat-model/)则记录了每项检查是为了阻止什么。
