The repository ships a working `fly.toml`. This page explains what is in it and why, so you can
adopt or adapt it deliberately.

<Steps>

1. **Create the app** and pick a region:

   ```bash
   fly launch --no-deploy
   ```

   Keep the shipped `fly.toml` when it asks — the sections below are load-bearing.

2. **Set the database connection string as a secret**:

   ```bash
   fly secrets set MONGODB_URI='mongodb+srv://user:password@cluster.example.mongodb.net'
   ```

   See [MongoDB Atlas](/docs/deploy/mongodb-atlas/) for the details of the string, including why the
   database name does not belong in it.

   For PostgreSQL, set `POSTGRES_URL` instead and skip `DATABASE_NAME` in the next step — the
   database name is part of that URL. Set one connection string, never both; see
   [PostgreSQL](/docs/deploy/postgresql/).

3. **Set the two non-secret variables** in `fly.toml`:

   ```toml
   [env]
     ISSUER = 'https://auth.example.com'
     DATABASE_NAME = 'OAuth'
   ```

   `ISSUER` must be the public URL browsers reach the app at, and it must be right the first time —
   the release command bakes it into the seeded console client's redirect URI once. Neither value is
   a credential, so neither needs to be a secret.

4. **Deploy**:

   ```bash
   fly deploy --remote-only
   ```

</Steps>

## The release command

```toml
[deploy]
  release_command = "sh -c 'bun run db:setup && bun run db:migrate'"
```

This is the most important line in the file. Fly runs it on a temporary Machine with the app's
environment, once per deploy attempt, **before** any new Machine serves traffic, and aborts the
deploy on a non-zero exit.

It has to run before the app serves, not after, because the seeds must exist for the deployment to
be usable at all: without the reserved admin project, bucket and client, `GET /admin/login`
redirects to `/auth` with a `client_id` no `Client` document matches, and the admin plane is
unreachable — while the first-run setup page at `GET /admin` still works, which makes it look like a
login bug rather than a missing seed. The same run provisions the TTL and unique-e-mail indexes that
the collections would otherwise be created without.

It also aborts the deploy usefully: `db:setup` exits non-zero when a constraint it declares is not
in force, so a database whose data violates a new unique index fails the deploy instead of silently
serving without it.

The release command needs the connection string, `DATABASE_NAME` on MongoDB, and `ISSUER` —
`ISSUER` included, because it is read for the admin client's `redirect_uri`. On PostgreSQL it is
`db:setup:pg`.

`db:migrate` follows in the same command because the server refuses to start against a database that
is behind the migrations its release declares. Left out, a release carrying its first migration
deploys an image that cannot boot; run from here, the same release is gated on the migration
succeeding. The declared set currently ships empty, so today the step reports `current` and exits —
which is the argument for wiring it before the first migration rather than with it. The `sh -c`
wrapper is what makes `&&` a shell operator instead of two more arguments to `bun`.

## The health checks

```toml
[[http_service.checks]]
  method = 'GET'
  path = '/health'
  interval = '30s'
  timeout = '5s'
  grace_period = '15s'
  headers = { X-Forwarded-Proto = 'https' }

[[http_service.checks]]
  method = 'GET'
  path = '/ready'
  interval = '60s'
  timeout = '10s'
  grace_period = '20s'
  headers = { X-Forwarded-Proto = 'https' }
```

Boot does a database connection and a keystore load at module scope, so a Machine that cannot reach
the datastore exits rather than serving. Without a check the proxy cannot tell that apart from a
healthy Machine and routes to it anyway.

Two details are deliberate. The `X-Forwarded-Proto = 'https'` header is a documented safeguard
against `force_https` turning the check into a `301` that the proxy reads as a failure. And the
15-second grace period covers a cold start, since `auto_start_machines` wakes Machines from stopped.

`GET /health` is the one route the rate limiter never counts — a refused liveness probe would take
the Machine out of the load balancer. It answers for the process alone, which is why the second
check exists: `GET /ready` reports whether the datastore is reachable, and Fly's checks stop routing
rather than restart, so a Machine whose database has gone away is shed instead of cycled. Its
interval is the longer of the two on purpose — the endpoint holds its last answer for a second and
shares one outstanding probe, so it cannot become database load, and there is nothing to gain from
asking twice a minute about something a deploy cannot fix.

## `rateLimit.trustedProxy` stays on

Fly's proxy sits in front of the app, so every request arrives from it. Leave
[`rateLimit.trustedProxy`](/docs/reference/settings/#rateLimit.trustedProxy) at its default of
`true`: with it off, every caller is counted as the proxy's own address, the whole internet shares
one allowance, and all traffic is refused within seconds. The origin resolver reads `Fly-Client-IP`
first, which is exactly the header Fly sets. [Behind a reverse proxy](/docs/deploy/reverse-proxy/)
covers the other direction, where the same default is wrong.

<Aside type="note" title="Deploys are manual on purpose">

The shipped `.github/workflows/deploy.yml` is `workflow_dispatch` only, with no push trigger,
because a deploy runs `db:setup` against a real datastore and should be an explicit act rather than a
side effect of merging. It takes the target as an input — which is only a choice of configuration
file — runs `bun test` first as a gate, deploys with `flyctl deploy --remote-only -c`, and then
probes both health endpoints and compares the advertised issuer with the one the config asks for.
That last comparison is the point: the issuer is the one value a deploy can get wrong in a way
nothing else catches, and reading the expected value out of the config is what stops the check from
merely agreeing with itself.

</Aside>

## The rest of the file

- `internal_port = 3000` matches the `EXPOSE 3000` in the Dockerfile and the port `bun start`
  listens on.
- `force_https = true`, so `ISSUER` is an `https` URL and HSTS (which the server emits
  unconditionally) is not a lie.
- `auto_stop_machines = 'off'` with `auto_start_machines = true`: the proxy never stops a Machine for
  want of traffic, so a request after a quiet night is served by a running process instead of waiting
  for a boot. `min_machines_running` is absent deliberately — it only means anything while something
  is allowed to stop Machines. Autostart stays on as a backstop, not for traffic: a Machine stopped
  by a host event comes back on the next request. A deployment nobody depends on yet wants the
  opposite, which is what the second configuration below is.
- `strategy = 'bluegreen'`: with a single Machine a rolling deploy replaces it in place, so every
  deploy costs a boot's worth of downtime. Blue-green boots the replacement alongside it and moves
  traffic once the new Machine's checks pass. It is available only because nothing here has a volume
  attached — blue-green and canary both refuse one.
- One shared-CPU VM with 1 GB of memory. Note that rate-limit counting is per instance and held in
  memory, so scaling to N Machines multiplies the effective allowance by N — see the caveat in
  [Kubernetes](/docs/deploy/kubernetes/), which applies identically here.

## The second configuration

The repository also ships `fly.conformance.toml`, which describes a separate Fly app: the instance
the OpenID conformance suite is pointed at. It is the same file with two answers reversed —
`auto_stop_machines = 'stop'` and `min_machines_running = 0`, so it costs nothing between runs, and
no blue-green strategy, because a test bed can afford a boot's downtime.

Deploy it with `fly deploy --remote-only -c fly.conformance.toml --ha=false`. The last flag is worth
knowing about: on the first deploy of a new app `flyctl` creates a second Machine for high
availability whatever the config says, and then advises setting `min_machines_running = 0` — which
this file already does, because the two settings are unrelated. Left as it lands, a test bed runs two
Machines whose in-memory rate-limit counters are independent, so the effective allowance is double
the configured one.

Two of its choices are worth borrowing for any second environment. It sets a different
`DATABASE_NAME`, so a run cannot write into production data and its console can be configured however
a test plan requires — server settings are per-database and boot-only, so sharing a database would
mean sharing them. And it stops rather than suspends, though suspending resumes faster: boot connects
to the datastore and loads the keystore at module scope, so a resumed process holds a connection pool
it established before it was frozen, and fails in a way that reads as a server defect rather than as
a cold start.
