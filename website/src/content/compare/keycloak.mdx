Keycloak is the server most teams weigh a self-hosted OAuth 2.1 deployment against. It is
older, broader — it also does SAML, realms, user federation and fine-grained authorization
services — and it runs on a different stack.

The rows below are what its own documentation says, on the date in the banner above. Where a
page did not answer the question, the row says "not documented" rather than guessing.

## Where each one fits

**Keycloak is the safer default if** you need SAML as well as OIDC, you already run the JVM and a
relational database, you want the realm and user-federation model, or a compliance reviewer
recognises the name. Its FAPI documentation is more extensive than ours, and its ecosystem of
adapters and themes is much larger.

**FoxAuth is the better fit if** your team writes TypeScript and would rather read the server than
wrap it, if you want an AI agent to administer the instance through the same permission checks and
audit trail a human uses, or if you want OAuth 2.1 behaviour — PKCE everywhere, exact redirect
matching, no Implicit grant — as the default rather than as per-client configuration.

The scope difference cuts both ways. FoxAuth does not do SAML, LDAP user federation or
policy-based fine-grained authorization; it does OAuth 2.1 and OpenID Connect, plus upstream OIDC
federation. If your list of requirements includes the first three, this is not a close call.

## Migrating

There is no importer. Clients are re-registered through the admin API or dynamic registration, and
end-user records are created per user bucket. Password hashes are not portable between the two, so
plan a reset-on-first-login window or run both servers during a cut-over.
