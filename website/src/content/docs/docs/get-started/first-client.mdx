A client is an application that asks this server for tokens. The console calls it an
**application**. Every application lives in a user bucket, and every bucket belongs to a group. That
is three concepts, but they nest, so the console walks them in order.

## Groups, buckets, applications

- A **group** owns things. Every user bucket carries an owning group, and belonging to that group is
  what grants access to the bucket and everything in it. There is no separate list of named
  managers. Each administrator already has a **Personal** group, which is usually a fine place for a
  first client; a **regular** group is a company or a team you share with colleagues.
- A **user bucket** is a population of end-users: their accounts, and the policy for how they
  register and verify themselves. It also holds the **applications** that sign those people in and
  the **APIs** they get tokens for. A bucket you create is also a tenant with **its own issuer** — it
  is served at `<ISSUER>/<slug>`, or at a hostname of its own, and mints tokens carrying that issuer,
  so an application in it integrates against that address rather than the bare one. The default
  `redfox` bucket is the exception: it keeps the bare issuer, which is what lets an existing
  deployment stay as it is.
- An **application** is an OAuth client. It belongs to the bucket it was created in for its whole
  life; no operation moves it to another bucket.

<Steps>

1. **Choose a group.** The dialog that creates a bucket asks which group it goes in, starting from
   the one chosen at the top of the console. Your **Personal** group is fine for a first client, but
   it has exactly one member, so work you will share belongs in a regular group, created under
   **Groups**, or is moved there later.

2. **Create a bucket** under **Buckets**. It takes a name and an address: a path, which becomes the
   last part of the issuer in its tokens, or a hostname of its own. Pick it deliberately: an issuer
   identifier is a promise made to every client configured against it, and changing it later is
   previewed and confirmed because every application in the bucket is affected. A new bucket is
   closed to sign-up unless you choose **Anyone who can reach the sign-in page**; you can change
   that later on its **Sign-in** tab.

   The Buckets table shows each bucket's address in its **Address** column. The reserved buckets read
   _served at the root_ there rather than a path, since they keep the bare issuer. Only a super
   administrator can add applications to the default `redfox` bucket, and nobody can add them to
   the administrators' bucket.

3. **Create a client** on the bucket's **Applications** tab, with **New client**. Pick the
   application type and the token endpoint authentication method, then enter the redirect URIs. The
   next section is about that choice. If browser code on another origin will call the token
   endpoint, list that origin under **Browser origins**; the list can be copied from another
   application of the same bucket.

</Steps>

## Public or confidential

The choice is the **token endpoint auth method**, and it follows from whether your application can
keep a secret:

| Method                 | Use for                                                                    | Credential                                   |
| ---------------------- | -------------------------------------------------------------------------- | -------------------------------------------- |
| `none` (public / PKCE) | Browser SPAs, mobile and desktop apps, CLIs: anything shipped to the user  | None. PKCE is the proof.                     |
| `client_secret_basic`  | Server-side web applications and back-end services                         | A secret, sent in the `Authorization` header |
| `client_secret_post`   | The same, where a client library can only put credentials in the form body | A secret, sent as a form field               |

PKCE is not optional here for either kind. Every authorization request with `response_type=code` is
refused without a `code_challenge`, and `S256` is the only accepted method. A request carrying
`plain` is rejected, and discovery advertises `S256` alone. A public client with no secret is
therefore not a weaker client; the code it receives is useless to anyone who did not generate the
verifier.

<Aside type="caution" title="The secret is shown once">

When a confidential client is created, or when you rotate its secret from the clients table, the
value appears in a dialog reading "Copy this secret now — it will not be shown again." It is not
recoverable afterwards. The way back is a rotation, which invalidates the old one.

</Aside>

## Redirect URIs match exactly

A redirect URI must be registered, and a request's `redirect_uri` is compared against the registered
set **as written**: scheme, host, port, path and query all have to match. `https://app.example.com/cb`
and `https://app.example.com/cb/` are two different URIs.

There is exactly one liberty, the one RFC 8252 §7.3 requires: a client whose application type is
**native** redirecting to `http:` on a loopback host may use any port. Everything else still matches
exactly. The liberty is narrow by design:

- native clients only; a web client's redirect is a real host it controls, so nothing about it is
  ephemeral;
- `http:` on a loopback host only; a claimed-`https` or private-scheme redirect stays exact;
- and `localhost` and `127.0.0.1` are **not** treated as interchangeable. Register both forms if
  your client might use either.

What stays open is a local port race: another process on the user's machine could bind the port and
receive the code. PKCE closes it, which is why it is mandatory.

## Which users a client signs in

Login routing is decided by the bucket a client belongs to, never by the client itself:

1. the reserved console client always goes to the administrator bucket;
2. an application created in a bucket goes to **that bucket**;
3. a client registered dynamically at a bucket's address (its `/reg`) belongs to that bucket;
4. a request that names one API declared at the address it was sent to goes to that API's bucket;
5. anything else (a client registered at the root, or one identified by a metadata document) goes
   to the default `redfox` bucket.

An application of the default `redfox` bucket is not pinned to it: rules 4 and 5 still apply to it.

The bucket is also where onboarding policy lives: whether registration is open
(`registrationOpen`), whether a new account must verify its e-mail
(`emailVerificationRequired`), whether that happens by link or by six-digit code
(`verificationMethod`), whether password sign-in is offered at all (`passwordLogin`), and whether an
authenticator app is required (`totpRequired`). None of it is set on the client. Two applications in
the same bucket share all of it, because they share the accounts.

<Aside type="note">

Consent is on by default (`consent.require` defaults to `true` for a new client), so the first
authorization request will show a consent screen. The reserved console client is the exception. It
is first-party and skips it.

</Aside>
