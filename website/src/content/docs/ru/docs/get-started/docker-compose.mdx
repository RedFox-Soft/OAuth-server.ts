Большинству быстрее всего увидеть работающий сервер авторизации с помощью Compose-файла, который
поставляется с репозиторием. Он поднимает три сервиса: MongoDB, одноразовый шаг подготовки базы данных и сам
сервер. Настраивать ничего не нужно, кроме `ISSUER`, о котором речь ниже.

**Требования:** Docker с Compose v2 (`docker compose`, а не старый `docker-compose`).

## Запуск трёх сервисов {#bring-it-up}

<Steps>

1. Скачайте Compose-файл:

   ```bash
   curl -O https://raw.githubusercontent.com/RedFox-Soft/OAuth-server.ts/main/docker-compose.yml
   ```

2. Определитесь со значением `ISSUER` сейчас; почему, объясняет предупреждение ниже. Если браузер
   будет обращаться к серверу не по адресу `http://localhost:3000`, измените `ISSUER` в **обоих** блоках
   `environment:` файла `docker-compose.yml`: в сервисе `setup` и в сервисе `oauth`. Если изменить
   только один, redirect URI, записанный при начальном заполнении, и объявленный issuer разойдутся, и
   такое расхождение нельзя исправить на месте.

3. Запустите всё:

   ```bash
   docker compose up
   ```

4. Откройте консоль по адресу `http://localhost:3000/admin`. При первом посещении показывается
   одноразовый экран настройки, на котором создаётся первый суперадминистратор.

</Steps>

## Что делают три сервиса {#what-the-three-services-do}

| Сервис  | Образ                                        | Роль                                                                                                                                                                                  |
| ------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mongo` | `mongo:8`                                    | Хранилище данных на именованном томе `mongo-data` с healthcheck через пинг `mongosh`, которого ждут остальные сервисы                                                                 |
| `setup` | `ghcr.io/redfox-soft/oauth-server-ts:latest` | Выполняет `bun run db:setup` и `bun run db:migrate`, затем завершается: коллекции, индексы, начальный ключ подписи RS256, начальные данные панели администратора и все миграции схемы |
| `oauth` | `ghcr.io/redfox-soft/oauth-server-ts:latest` | Сам сервер на порту 3000; запускается только после успешного завершения `setup`                                                                                                       |

Сервер ждёт `setup` по двум причинам. Без зарезервированного проекта администраторов и клиента `admin-panel`,
которые создаёт `setup`, вход в консоль перенаправляет на клиент, которому не соответствует ни один
документ `Client`. Страница первоначальной настройки в таком состоянии всё равно работает, и из-за
этого проблема может выглядеть как ошибка входа. Кроме того, сервер отказывается запускаться с базой
данных, миграции которой не применены, поэтому `setup` выполняет `db:migrate` после `db:setup`. Обе
команды можно безопасно запускать повторно, так что для обновления достаточно загрузить более
новый образ и снова выполнить `docker compose up`; сначала сделайте резервную копию, если в примечаниях к
релизу названа миграция, которую нельзя отменить.

<Aside type="caution" title="Задайте ISSUER до первого docker compose up">

`ISSUER` должен быть URL, по которому браузер обращается к серверу, и его значение должно быть
окончательным **до** первого `up`. Redirect URI клиента администратора из начальных данных выводится из
него один раз, через `$setOnInsert` (значение записывается только при создании документа), и
последующее изменение не исправляется повторным запуском `db:setup`.

Если вы уже запустили сервер с неверным значением, удалите хранилище данных и начните
заново:

```bash
docker compose down -v   # removes the mongo-data volume
# edit ISSUER in docker-compose.yml
docker compose up
```

При удалении тома уничтожаются все учётные записи, клиенты и ключи подписи в нём, так что такой
обходной путь годится только для первого дня. В развёртывании, где уже есть данные, неверный `ISSUER` через консоль не исправить:
консоль не даёт изменить только один клиент, зарезервированный клиент администратора. Поэтому
`ISSUER` должен быть верным до первого запуска.

</Aside>

## Адреса, которые стоит открыть после запуска {#where-to-go-next}

- Консоль по адресу `http://localhost:3000/admin`, где вы [создаёте первого администратора](/ru/docs/get-started/first-admin/).
- Документ discovery, авторитетный список URL эндпоинтов для клиентской библиотеки:
  `http://localhost:3000/.well-known/openid-configuration`.
- Набор ключей: `http://localhost:3000/jwks`.
- Проба liveness, на которую никогда не действует ограничение частоты запросов:
  `http://localhost:3000/health`, и её пара для readiness `http://localhost:3000/ready`, которая также
  обращается к базе данных.

`docker-compose.yml` запускает MongoDB. Лежащий рядом `docker-compose.postgres.yml` описывает те же три сервиса на
PostgreSQL и запускается командой `docker compose -f docker-compose.postgres.yml up`. Эти два файла
альтернативны: никогда не используйте их вместе. Какая переменная выбирает какую базу данных, см. в разделе
[PostgreSQL](/ru/docs/deploy/postgresql/).

Compose-файл, ориентированный на продакшен (с закреплёнными тегами, внешней базой данных и
TLS-прокси перед сервером), описан в разделе [Развёртывание с Docker
Compose](/ru/docs/deploy/docker-compose/).
