Клиентом называют приложение, которое запрашивает у этого сервера токены. В консоли клиент называется
**приложением** (application). Каждое приложение находится в проекте, а каждый проект принадлежит
команде. Команды, проекты и приложения вложены друг в друга, поэтому консоль проводит по ним в этом
порядке.

## Команды владеют проектами, проекты содержат приложения {#teams-projects-applications}

- **Команда** чем-то владеет. У каждого проекта есть команда-владелец, и именно членство в этой
  команде даёт доступ к проекту и всему, что в нём есть. Отдельного списка назначенных управляющих
  нет. У каждого администратора уже есть **личная команда**, и для первого клиента её обычно вполне
  достаточно. **Обычной** командой (regular) называют компанию или круг коллег, с которыми вы делите
  работу.
- **Проект** объединяет конечных пользователей: их учётные записи и политику того, как они
  регистрируются и подтверждают себя. В нём же лежат **приложения**, через которые эти люди входят,
  и **API**, для которых они получают токены. Созданный вами проект служит ещё и тенантом со **своим
  собственным издателем (issuer)**. Он обслуживается по адресу `<ISSUER>/<slug>`, на поддомене
  экземпляра или по собственному имени хоста и выпускает токены с этим issuer. Поэтому приложение в нём
  интегрируется с этим адресом, а не с корневым issuer (самим `ISSUER`). Проект по умолчанию `redfox`
  составляет исключение: он сохраняет корневой issuer, и именно это позволяет существующему
  развёртыванию остаться как есть.
- **Приложением** в консоли называется OAuth-клиент. Оно принадлежит проекту, в котором создано, всю свою жизнь;
  перенести его в другой проект нельзя никакой операцией.

<Aside type="note" title="В FoxAuth Cloud">

Сначала создайте собственный проект. Добавлять приложения в проект `redfox` по умолчанию может только
суперадминистратор, поэтому новая учётная запись этого не может. На тарифе Free имя в адресе проекта сервер
генерирует сам: восемь букв и цифр. Проект получает собственный поддомен, поэтому издателем будет
`https://<имя>.auth.foxauth.dev`. В проекте на Free помещается до 10 приложений.

</Aside>

<Steps>

1. **Выберите команду.** Диалог создания проекта спрашивает, в какую команду его поместить, и
   начинает с команды, выбранной вверху консоли. Для первого клиента подойдёт ваша личная команда.
   В ней ровно один член, поэтому общую работу стоит вести в обычной команде: создайте её в
   разделе **Teams** или перенесите проект туда позже.

2. **Создайте проект** в разделе **Projects** кнопкой **New project**. Для него нужны имя и адрес:
   путь, который становится последней частью issuer в его токенах, или поддомен вроде
   `acme.auth.example.com`, если экземпляр его предлагает. Поддоменом называют имя на один уровень ниже
   хоста экземпляра. Суперадминистратор может дать проекту и собственное имя хоста. Все три вида адреса
   сравнивает страница [Project addresses](/ru/docs/administer/project-addresses/).
   Выбирайте адрес обдуманно: идентификатор issuer равносилен обещанию, данному каждому клиенту,
   который на него настроен. Смена адреса позже касается каждого приложения в проекте, поэтому перед
   сменой показывается, что она затронет, и требуется подтверждение. Новый проект закрыт для регистрации,
   если не выбрать **Anyone who can reach the sign-in page**. Изменить это можно позже на вкладке
   **Sign-in** проекта.

   В таблице Projects адрес каждого проекта показан в столбце **Address**. У зарезервированных
   проектов там вместо пути написано _served at the root_, поскольку они сохраняют корневой issuer.
   Добавлять приложения в проект по умолчанию `redfox` может только суперадминистратор, а в проект
   администраторов их не может добавить никто.

3. **Создайте приложение** на вкладке **Applications** проекта кнопкой **New application**. Выберите
   ситуацию, которая подходит вашему приложению: веб-приложение с сервером, одностраничное приложение,
   мобильное, десктопное или консольное приложение, устройство без клавиатуры или сервис, который
   обращается к вашему API. Затем укажите, где приложение работает во время разработки, например
   `http://localhost:3000`. Консоль сама заполнит настройки протокола, о которых говорит следующий
   раздел, а также адреса возврата после входа и после выхода; их можно поправить. После этого
   откроется собственная страница приложения на вкладке **Connect**: client ID, issuer и адрес discovery
   проекта и блок конфигурации, который нужно вставить в приложение. Чтобы задать всё вручную, выберите
   **Configure everything yourself** или **Show all settings**.

   Защита MCP-сервера или API не считается приложением. Выберите карточку для неё, и консоль перейдёт на
   вкладку **APIs** проекта, где API объявляют; хосты агентов, которые к нему обращаются, получают собственный
   идентификатор клиента.

4. **Пустите кого-нибудь войти.** В новом проекте нет ни одного человека, и регистрация в нём закрыта,
   поэтому первый вход через ваше приложение никого бы не пустил. Вкладка Connect говорит об этом и
   предлагает два пути: пригласить себя тестовым пользователем или открыть регистрацию. Когда ваше
   приложение впустит кого-то, статус вверху его страницы покажет, когда это было.

</Steps>

## Публичный или конфиденциальный {#public-or-confidential}

Выбранная ситуация сама задаёт **метод аутентификации на эндпоинте токенов** (token endpoint auth
method). Метод следует из того, может ли ваше приложение хранить секрет. Изменить его можно на вкладке
**Settings** приложения:

| Метод                     | Для чего                                                                                   | Учётные данные                                   |
| ------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| `none` (публичный / PKCE) | SPA в браузере, мобильные и десктопные приложения, CLI: всё, что поставляется пользователю | Нет. Доказательством служит PKCE.                |
| `client_secret_basic`     | Серверные веб-приложения и бэкенд-сервисы                                                  | Секрет, передаваемый в заголовке `Authorization` |
| `client_secret_post`      | То же самое, когда клиентская библиотека может передать учётные данные только в теле формы | Секрет, передаваемый в поле формы                |

PKCE здесь не опционален ни для одного из видов. Любой запрос авторизации с `response_type=code`
без `code_challenge` отклоняется, а из методов принимается только `S256`. Запрос с `plain`
отклоняется, и discovery объявляет только `S256`. Поэтому публичный клиент без секрета не становится
более слабым клиентом: полученный им код бесполезен для любого, кто не генерировал verifier.

<Aside type="caution" title="Секрет показывается один раз">

Когда создаётся конфиденциальное приложение, его секрет показывается один раз: на странице
приложения, внутри блока конфигурации. Восстановить его потом нельзя. Выход только один: ротация. При
ней старый секрет перестаёт действовать, а новый один раз показывается там же. Блок никогда не
кладёт секрет в переменную с таким именем, которое фронтенд-сборка отдала бы каждому посетителю.

</Aside>

## Redirect URI сравниваются точно {#redirect-uris-match-exactly}

Redirect URI должен быть зарегистрирован, а `redirect_uri` из запроса сравнивается с
зарегистрированным набором **как написано**: схема, хост, порт, путь и query должны совпадать.
`https://app.example.com/cb` и `https://app.example.com/cb/` считаются двумя разными URI.

Есть ровно одно послабление, и его требует RFC 8252 §7.3: клиент с типом приложения
**native**, перенаправляющий на `http:` на loopback-хосте, может использовать любой порт. Всё
остальное по-прежнему должно совпадать точно. Послабление намеренно узкое:

- только для native-клиентов; redirect веб-клиента ведёт на реальный хост под его контролем, так что
  ничего эфемерного в нём нет;
- только `http:` на loopback-хосте; redirect на закреплённый за приложением (claimed) `https`-адрес
  или на приватную схему по-прежнему сравнивается точно;
- `localhost` и `127.0.0.1` **не** считаются взаимозаменяемыми. Зарегистрируйте обе формы, если
  ваш клиент может использовать любую из них.

Открытой остаётся гонка за локальный порт: другой процесс на машине пользователя может занять порт
и получить код. Эту гонку закрывает PKCE, и именно поэтому PKCE обязателен.

## Каких пользователей впускает клиент {#which-users-a-client-signs-in}

Маршрутизацию входа всегда определяет проект, которому принадлежит клиент, а не сам клиент:

1. зарезервированный клиент консоли всегда направляется в проект администраторов;
2. приложение, созданное в проекте, направляется в **этот проект**;
3. клиент, динамически зарегистрированный по адресу проекта (его `/reg`), принадлежит этому проекту;
4. запрос, который называет один API, объявленный по адресу, куда пришёл запрос, направляется в
   проект этого API;
5. всё остальное (клиент, зарегистрированный в корне, или клиент, заданный документом метаданных)
   направляется в проект по умолчанию `redfox`.

Приложение проекта по умолчанию `redfox` к нему не привязано: правила 4 и 5 к нему по-прежнему
применяются.

В проекте же задаются правила регистрации и входа новых пользователей: открыта ли регистрация
(`registrationOpen`), должна ли новая учётная запись подтвердить e-mail
(`emailVerificationRequired`), происходит ли это по ссылке или по шестизначному коду
(`verificationMethod`), предлагается ли вообще вход по паролю (`passwordLogin`) и обязательно ли
приложение-аутентификатор (`totpRequired`). Ничего из этого не задаётся на клиенте. Два приложения в
одном проекте разделяют эти правила, потому что разделяют учётные записи.

Требует ли проект подтверждения адреса, решает только то, кто может войти. Что сообщается приложениям, от этого
не зависит. Адрес новой учётной записи считается подтверждённым, и приложения получают `email_verified: true`,
только после проверки: по ссылке из письма, через доверенного провайдера входа или когда администратор отмечает
адрес подтверждённым.

<Aside type="note">

Согласие включено по умолчанию (`consent.require` для нового клиента по умолчанию равно `true`),
поэтому первый запрос авторизации покажет экран согласия. Зарезервированный клиент консоли составляет
исключение: он собственный (first-party) и этот экран пропускает.

</Aside>
