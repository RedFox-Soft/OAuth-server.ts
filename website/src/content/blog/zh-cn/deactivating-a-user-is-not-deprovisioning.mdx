以我们自己的服务器 0.7.0 版为例。在控制台中停用一个最终用户，然后把该用户的应用程序十分钟前拿到的不透明访问令牌发给内省端点。回答是 `"active": true`。在该用户的浏览器里打开应用程序，他们仍处于登录状态。查看应用程序的日志：没有任何消息告诉它情况已经变了。

从狭义上说，没有任何东西坏掉。账户处于停用状态，每个解析账户的地方都检查了这个标志：新的登录被拒绝，刷新被拒绝，设备流程和 CIBA 也被拒绝。大多数停用功能都是这样工作的。我发布它时相信这就够了，因为就我当时提出的问题——「这个人能进来吗？」——而言，这项检查放在了正确的位置。而管理员在停用某人时（通常是在匆忙之中）真正要问的是「这个人出去了吗？」这两个问题的答案不同，二者之间的差距，就是点击之前签发的每一个会话和令牌。

## 下次登录时才检查的标志终结不了任何东西 {#a-flag-checked-at-the-next-sign-in-ends-nothing}

标志是对未来的陈述。它拦住下一次登录。账户已经持有的一切，都是由当时通过的检查授予的，而没有任何东西会让那项检查重新执行一次。授权服务器上的浏览器会话在过期之前一直有效。访问令牌在其 `exp` 之前一直有效；如果它是不透明令牌，内省也会一直这样回答，因为内省问的是令牌及其授权（grant）是否存在，而不是它们背后的账户此后是否被禁用。依赖方自己的会话，也就是用户实际看到的那个会话，存活多久由依赖方决定，而从来没有人通知过依赖方。

所以取消预配不是一个标志。它是一个标志，再加上一个操作，去找出标志够不着的一切。而这个操作中各步骤的顺序，比我预想的更重要。

## 先读取会话，再清除它们 {#read-the-sessions-before-you-sweep-them}

显而易见的实现只有两行：设置 `active: false`，然后删除该账户拥有的一切。它错在一个任何「会话已清除」的测试都看不到的地方。必须通知依赖方：每个会话发送一个 OpenID Connect 后端通道登出令牌，而每个登出令牌都携带该会话的 `sid`。会话记录是唯一保存它的地方。先删除，你就再也没有东西可以用来通知谁了。每个会话都被正确地清除，而每个依赖方都让它的用户继续保持登录。

所以顺序是固定的，并且直接写在函数本身里，而不是交给一条注释：

```ts
export async function revokeAccountAccess(
	accountId: string
): Promise<CascadeResult> {
	await notifyRelyingParties(accountId);
	return sweepAccountOwned(accountId);
}
```

`notifyRelyingParties` 读取该账户拥有的每个会话，为此需要在全部三个存储适配器上新增一个方法：`findByOwner`。在此之前，枚举某个主体的记录的唯一办法，就是销毁这些记录的那个方法。一个无法访问的依赖方不会中止这个操作。它的失败会作为事件上报，与普通登出时一样：一个必须失去访问权限的账户，不会仅仅因为某个应用程序的登出端点宕机就保留访问权限。

清除本身并不是一份凭某人记忆列出的表清单。我们服务器中的每个存储区域都声明了自己的哪个字段标识所有者，而清除就是基于这份声明的过滤。因此，后续版本新增的区域会因为它存在而被清除，而不是因为有人在级联操作里加了一行。这种手工维护的版本我写过不止一次，它会在第一次新增区域时悄无声息地失效：新记录就这样比账户活得更久，而没有任何东西提示这一点。另一种显而易见的设计——遍历账户的授权——会漏掉清除所覆盖的大部分内容，因为会话、进行中的登录、第二因素绑定和邮箱验证质询都挂在账户上，而不是挂在任何授权上。

内省完全不需要改动。只要令牌背后的授权不存在了，它本来就会回答 `active: false`，所以清除授权就能一次性让所有不透明访问令牌失效。

## 登录节流不是访问权限 {#the-login-throttle-is-not-access}

清除在两个与账户有着松散关联的区域前止步：登录节流和密码重置节流，两者都以电子邮件地址为键。很容易把这理解为疏漏。恰恰相反。这些记录不是访问权限，而是针对该地址的猜测次数。你最可能匆忙停用一个账户的时刻，恰恰是它正遭受攻击的时刻。那时清除节流记录，就是在事件处理中途重置暴力破解计数器，让攻击者受益。所以规则是：清除终结那些让人进来的东西，保留那些把人挡在外面的东西。

## 部分清除必须返回 500 {#a-partial-sweep-has-to-answer-500}

我们的管理路由在变更之前写入审计记录，而审计日志是只追加的。两者都是好规则，但合在一起，就让报告部分失败的那种显而易见的设计变得不可能：你无法把「这三个区域未能清除」写进一条在你尝试之前就已写好的记录里。

所以一次清除后留有残余的停用会返回 `500`，并列出存活下来的区域。该账户已经无法登录，因为标志是最先写入的。残留的东西最多存活到各自区域的过期时间，绝不会成为重新进入的途径。停用一个已经处于停用状态的账户也是允许的：它会再清除一次，而不是被当作空操作拒绝，因为这次重复就是恢复手段。在你真正需要它之前，这看起来像是一个奇怪的幂等性选择。

## 锁定不是 active，因为 active 属于目录 {#lock-is-not-active-because-active-belongs-to-the-directory}

一旦某个用户由 SCIM 目录管理，`active` 标志就归目录所有。Entra 或 Okta 设置它，下一次同步又会再设置一次。管理员在事件响应中于本地停用一个预配用户，几分钟后他的决定就会被一个定时任务悄悄推翻。这样的控制手段，任何人都不应依赖。

所以锁定是第二个标志，只由管理员写入，而登录检查是两者的合取，放在一个每道门都会调用的函数里。最后这一点和标志本身同样重要。「这个用户能否进入」的两份副本会逐渐偏离，而偏离的那一份就是被锁定用户走进来的那道门。我们的副本就曾经偏离过一次：联合登录路径只读取 `active`，所以被锁定账户已有的上游关联通过了那一步，直到下一道门才识别出锁定。

锁定偏离了 OpenID 的 IPSIE 规范（profile，全称 Interoperability Profiling for Secure Identity in the Enterprise），该规范禁止在本地更改由身份服务管理的用户，对此我坦然接受。它只涉及登录，从不触及用户资料，而一个必须等别人的系统完成同步的事件响应，就不算事件响应。

锁定执行与停用相同的清除。我们特意让解锁变得更难：对通过 MCP 控制平面操作的 AI 智能体而言，它是一个后果严重、需要确认的操作，因为它会重新放行一个被管理员判定为已失陷的账户。

顺便说一句，重新激活和解锁不会恢复任何东西。授权同意随授权一起被清除了，所以用户登录后要重新同意一次。人们第一次遇到时会感到意外，但这正是 IPSIE 中「all access mechanisms and authorizations」（所有访问机制和授权）的含义。

## 你够不着的令牌 {#the-token-you-cannot-reach}

有一样东西是整个操作碰不到的。与其让「停用会立即终止访问」这句话不加限定地摆在那里，不如直接说清楚。资源服务器自行用已发布的密钥校验的 JWT 访问令牌，永远不会回到授权服务器。既没有可以拦截的调用，也没有一条资源服务器会去查询、而我们又能删除的记录。它会一直存活到它的 `exp`。

唯一的杠杆是有效期。在我们的服务器中，已声明资源（管理员登记为受保护资源的 API 或 MCP 服务器）的令牌有效期是十五分钟，除非管理员调高它，最长可以调到一天。IPSIE SL2 允许未绑定密钥的令牌有效十五分钟，用 DPoP 绑定的令牌有效六十分钟，这合理地回答了一个问题：一个组织应当能容忍离职员工的令牌继续工作多久。如果某个资源服务器连这都无法接受，它可以要求使用不透明令牌并对其做内省，以每个请求一次往返的代价，在停用发生的那一刻就看到它。我参与过的大多数资源服务器宁愿要那十五分钟。

## 每个按钮各在何时适用 {#when-each-one-is-the-right-button}

当这个人不应该进入、并且账户归你所有时，停用。当你现在就需要这个结果、而账户归目录所有时，或者当你不信任下一次同步时，锁定。当人没问题、而设备有问题时，用「Sign out everywhere」（在所有地方登出）让该用户全部登出，我们的服务器把它作为单独的操作提供：它执行同样的清除，并保持账户处于激活状态。当记录本身应该消失时，删除。删除同样会终止访问，因为它会先执行同样的序列。

围绕这一切的某些机制出现得比清除本身更晚。目录通过预配连接与我们的服务器对接，预配连接是把一个目录与一个用户桶关联起来的记录（用户桶是本服务器对一组最终用户的称呼，这组用户有自己的登录规则，一旦有了地址，也有自己的签发者）。有一种保护机制会在这样的连接开始一次性取消预配过多用户时将其挂起，它已经通过了测试。但 Okta 针对真实组织的 CRUD 测试还没有运行过，也没有 `/Bulk` 端点。Okta 的 Universal Logout 会从上游调用同一个清除，它从未在真实的 Okta 组织上运行过。这些都没有提交认证。清除本身已在一台运行中的服务器上端到端走通：登出令牌已送达，刷新和内省被拒绝，重新激活后再次要求授权同意。我会照搬的，正是这一部分。
