客户端是向本服务器请求令牌的应用，控制台称之为**应用**（application）。每个应用都位于一个项目中，而每个项目都归属于一个团队。团队、项目和应用层层嵌套，所以控制台会按这个顺序依次引导你。

## 团队拥有项目，项目包含应用 {#teams-projects-applications}

- **团队**拥有资源。每个项目都有一个所属团队，属于该团队就是获得该项目及其中一切的访问权限的方式，不存在单独的具名管理者列表。每个管理员都已经有一个**个人团队**，通常很适合用来放第一个客户端。**regular**（常规）团队则对应公司，或你与之共享工作的一群同事。
- **项目**是一群最终用户：他们的账户，以及他们如何注册和验证身份的策略。它还包含让这些人登录的**应用**，以及他们获取令牌所针对的 **API**。你创建的项目同时也是一个拥有**自己的签发者**（issuer）的租户。它在 `<ISSUER>/<slug>` 下、在实例的子域名下或在自己的主机名下提供服务，签发的令牌也带有这个签发者。因此其中的应用要对接这个地址，而不是不带路径的根签发者（即 `ISSUER` 本身）。默认的 `redfox` 项目是例外：它沿用不带路径的签发者，正因如此，现有部署才能保持原样。
- **应用**就是 OAuth 客户端。它在整个生命周期内都属于创建它的那个项目，没有任何操作能把它移到另一个项目。

<Aside type="note" title="在 FoxAuth Cloud 上">

先创建一个你自己的项目。只有超级管理员才能向默认的 `redfox` 项目添加应用，新账户不能。在 Free 方案中，项目地址里的名称由服务器生成，是八位字母和数字。项目使用自己的子域名，因此你的签发者就是 `https://<名称>.auth.foxauth.dev`。一个 Free 项目最多容纳 10 个应用。

</Aside>

<Steps>

1. **选择团队**。创建项目的对话框会询问它归入哪个团队，默认是控制台顶部选中的那个团队。第一个客户端放在你的个人团队里就可以。该团队只有你一个成员，所以需要与他人共享的工作应放在常规团队中：在 **Teams** 下创建一个，或者以后再把项目移过去。

2. 在 **Projects** 下点击 **New project** **创建项目**。它需要一个名称和一个地址：一个路径（会成为其令牌中签发者的最后一部分），或者在实例提供时选择一个子域名，例如 `acme.auth.example.com`。子域名是实例主机名下一级的名称。超级管理员还可以为项目指定一个独立的主机名。[Project addresses](/zh-cn/docs/administer/project-addresses/) 页面比较了这三种地址。请慎重选择：签发者标识符是对每个按它配置的客户端作出的承诺，以后更改地址会影响该项目中的每个应用，因此会先预览影响并要求确认。新项目默认不开放注册，除非你选择 **Anyone who can reach the sign-in page**；以后可以在它的 **Sign-in** 标签页上更改。

   Projects 表在 **Address** 列中显示每个项目的地址。保留的项目在这一列显示的是 _served at the root_（在根路径提供服务），而不是路径，因为它们沿用不带路径的签发者。只有超级管理员可以向默认的 `redfox` 项目添加应用，任何人都不能向管理员项目添加应用。

3. 在项目的 **Applications** 标签页上点击 **New application** **创建应用**。选择与你的应用相符的情形：带服务器的 Web 应用、单页应用、移动端/桌面端/命令行应用、没有键盘的设备，或者调用你的 API 的服务。然后填写开发期间应用运行的地址，例如 `http://localhost:3000`。控制台会自动填好下一节介绍的协议设置，以及登录后和退出后的返回地址，这些地址仍可修改。随后会打开该应用自己的页面，停在 **Connect** 标签页上：client ID、项目的签发者和发现地址，以及一段要粘贴到应用中的配置。如果想手动设置所有内容，请选择 **Configure everything yourself** 或 **Show all settings**。

   保护 MCP 服务器或 API 并不是创建应用。选择对应的卡片后，控制台会带你到项目的 **APIs** 标签页去声明这个 API；调用它的智能体宿主会获得各自的客户端身份。

4. **让人能够登录。** 新项目里没有任何人，也不开放注册，所以第一次通过你的应用登录时没有人能进来。Connect 标签页会说明这一点，并提供两种办法：把自己邀请为测试用户，或者开放注册。当你的应用让某人登录后，页面顶部的状态会显示那是什么时候。

</Steps>

## 公开客户端还是机密客户端 {#public-or-confidential}

你选择的情形会替你设定**令牌端点认证方式**。认证方式取决于你的应用能否保守密钥。你可以在应用的 **Settings** 标签页上更改它：

| 方式                  | 适用于                                                    | 凭据                                      |
| --------------------- | --------------------------------------------------------- | ----------------------------------------- |
| `none`（公开 / PKCE） | 浏览器 SPA、移动和桌面应用、CLI：任何交付到用户手中的程序 | 无。PKCE 就是证明。                       |
| `client_secret_basic` | 服务端 Web 应用和后端服务                                 | 一个密钥，通过 `Authorization` 请求头发送 |
| `client_secret_post`  | 同上，但客户端库只能把凭据放在表单正文中                  | 一个密钥，作为表单字段发送                |

在这里，无论哪种客户端，PKCE 都不是可选的。每个 `response_type=code` 的授权请求如果没有 `code_challenge` 都会被拒绝，而 `S256` 是唯一接受的方法。携带 `plain` 的请求会被拒绝，发现文档也只公布 `S256`。因此，没有密钥的公开客户端并不是更弱的客户端；它收到的授权码对没有生成 verifier 的人毫无用处。

<Aside type="caution" title="密钥只显示一次">

创建机密应用时，它的密钥只显示一次：在应用页面的配置块中。之后无法找回。唯一的补救办法是轮换：旧密钥随即失效，新密钥同样只在原处显示一次。配置块绝不会把密钥放进前端构建会发给每位访问者的变量名下。

</Aside>

## 重定向 URI 精确匹配 {#redirect-uris-match-exactly}

重定向 URI 必须事先注册，请求中的 `redirect_uri` 会与已注册的集合**按原样**比较：scheme、主机、端口、路径和查询字符串都必须一致。`https://app.example.com/cb` 和 `https://app.example.com/cb/` 是两个不同的 URI。

只有一处例外，也就是 RFC 8252 §7.3 所要求的那一处：应用类型为 **native** 的客户端，重定向到回环主机上的 `http:` 地址时，可以使用任意端口。其余部分仍须精确匹配。这个例外是刻意收窄的：

- 仅限 native 客户端；Web 客户端的重定向目标是它所控制的真实主机，没有任何部分是临时的；
- 仅限回环主机上的 `http:`；claimed `https` 重定向或私有 scheme 重定向仍须精确匹配；
- 并且 `localhost` 和 `127.0.0.1` **不**被视为可以互换。如果你的客户端可能用到其中任何一种，就把两种形式都注册上。

仍然存在的是本地端口竞争：用户机器上的另一个进程可能抢先绑定该端口并收到授权码。PKCE 堵住了这种端口竞争，这也是 PKCE 被强制要求的原因。

## 客户端为哪些用户提供登录 {#which-users-a-client-signs-in}

登录路由由客户端所属的项目决定，而绝不由客户端本身决定：

1. 保留的控制台客户端总是进入管理员项目；
2. 在某个项目中创建的应用进入**该项目**；
3. 在某个项目的地址（其 `/reg`）动态注册的客户端属于该项目；
4. 如果请求指明了一个在其所发往地址下声明的 API，就进入该 API 所在的项目；
5. 其他情况（在根地址注册的客户端，或由元数据文档标识的客户端）进入默认的 `redfox` 项目。

默认 `redfox` 项目中的应用并不固定在该项目：规则 4 和 5 对它仍然适用。

项目也是注册引导策略所在之处：是否开放注册（`registrationOpen`）、新账户是否必须验证电子邮件（`emailVerificationRequired`）、验证是通过链接还是六位数验证码（`verificationMethod`）、是否提供密码登录（`passwordLogin`），以及是否要求使用身份验证器应用（`totpRequired`）。这些都不在客户端上设置。同一项目中的两个应用共享全部这些设置，因为它们共享同一批账户。

项目是否要求验证电子邮件，只决定谁可以登录，不决定告诉应用什么。新账户的地址只有在被证明之后才算已验证，应用也才会收到 `email_verified: true`：证明方式是邮件中的链接、受信任的身份提供方，或由管理员标记为已验证。

<Aside type="note">

授权同意默认开启（新客户端的 `consent.require` 默认为 `true`），因此第一次授权请求会显示授权同意页面。保留的控制台客户端是例外：它是第一方客户端，会跳过这一步。

</Aside>
