需求听上去很简单。一家公司的用户通过他们的员工身份提供商登录我们的授权服务器；当这家公司的安全团队决定某个人的访问必须终止——在所有地方、立刻——身份提供商应当能够通知我们。不是在下一次登录时，那可能要等到明天。而是现在：会话、刷新令牌，统统终止。

于是我去找身份提供商告诉依赖方「终止这个人拥有的一切」的标准方式。并不存在。有一份针对更窄场景的最终规范，有一份针对更宽场景、但大型提供商并不向第三方发送的规范，还有一份未被采纳便已过期的个人 Internet-Draft，而它恰好就是 Okta 发送的那一份。

## 只有一家大型员工 IdP 会推送「终止一切」，而它推送的是一份草案 {#only-one-big-workforce-idp-pushes-end-everything-and-it-pushes-a-draft}

以下是截至 2026 年 10 月，每家提供商实际会向我们这样的应用发送的内容。比营销页面所暗示的要少。

后端通道登出（back-channel logout）是 OpenID 的一份最终规范，而且是一份好规范，但它报告的是一次登出，而不是一次失陷：它终止源自同一个上游会话的那些会话，而离线访问按设计应当在它之后继续存在。Shared Signals 和 CAEP 是表达「此会话已撤销」的通用标准，但大型员工身份提供商中没有一家会把它们推送给任意依赖方。Entra 对第三方客户端什么都不发送。剩下的就是 Okta 的 Universal Logout（通用登出），也就是 draft-parecki-oauth-global-token-revocation。第 06 版发布于 2026 年 2 月。它于 8 月 28 日过期，OAuth 工作组没有采纳它，也没有 `draft-ietf-` 后继版本。我们考察了十六款同类产品，其中恰好只有另外一款，即 Auth0，会接收这个请求。

我还是把它做出来了，而且我认为这样做是对的，但前提是三条保险措施；如今对任何建立在过期草案之上的东西，我都会坚持这三条。目标是 Okta 文档中写明的那个请求，而不是把草案当成标准来读。一切都置于它自己的开关之后，即 `globalTokenRevocation.enabled`，默认关闭，控制台里对它的说明写明了草案已经过期。而线路格式（wire format）是一个小模块，位于一个对它一无所知的核心之上，这样当格式变化或者消亡时，决定谁可以终止谁的访问的那部分不必改动。

## Okta 实际发送的内容 {#what-okta-actually-sends}

Okta 以 POST 发送一个指明用户的 JSON 请求体，并附带一个用它自己的密钥签名的 bearer JWT：

```http
POST /acme/global-token-revocation HTTP/1.1
Host: auth.example.com
Authorization: Bearer eyJ0eXAiOiJnbG9iYWwtdG9rZW4tcmV2b2NhdGlvbitqd3QiLCJhbGciOiJSUzI1NiJ9...
Content-Type: application/json

{ "sub_id": { "format": "iss_sub", "iss": "https://acme.okta.com", "sub": "00u1a2b3c4d5e6f7g8h9" } }
```

解码之后，断言说明了是谁在请求、针对的是哪个端点：

```json
{ "typ": "global-token-revocation+jwt", "alg": "RS256", "kid": "q8J1..." }
{
  "iss": "https://acme.okta.com",
  "sub": "0oa1b2c3d4e5f6g7h8i9",
  "aud": "https://auth.example.com/acme/global-token-revocation",
  "iat": 1759917600,
  "nbf": 1759917300,
  "exp": 1759917900,
  "jti": "1a8c3e0f-5b2d-4c7e-9f61-2d0b8a4e7c35"
}
```

`iss` 是 Okta 组织，`sub` 是我们在那边的客户端 ID，因此这一对值标识的是配置在某一个桶上的某一个上游提供商。请求体中的 `sub_id` 标识的是人：用他在该提供商处的 subject，或者按 Okta 的另一种格式，用电子邮件地址。只有当该提供商让某个用户在这里登录，或者它所绑定的 SCIM 连接预配了这个用户时，这个用户才能被指名。其他所有人，包括根本不存在的人，都会得到同样的 `404`，因此这个端点无法被用来探查谁拥有账户。

它终止的是一切：会话、授权（grant）、刷新令牌和不透明访问令牌，并向每个依赖方发出后端通道登出。账户保持启用，所以这个人可以立刻重新登录，并重新给出授权同意。这超出了草案的 MUST，即刷新令牌加上重新认证，而草案允许这样做。所有路径共用同一个终止访问的操作，是我们有意做出的决定，我们的管理员通过「Sign out everywhere」得到的也是同样的效果。

## 有效期从 iat 算起，绝不从 nbf 算起 {#measure-the-lifetime-from-iat-never-from-nbf}

看看那个载荷里的三个时间。`nbf` 比 `iat` 早五分钟，`exp` 比它晚五分钟。Okta 是有意这么做的，为的是容忍接收方的时钟偏差，这完全正当。

我们把所出示断言的有效期上限定为 300 秒，因为长寿命的断言意味着很长的重放窗口。衡量 JWT 有效期最直观的方式，是从它开始生效算到它失效，即 `exp - nbf`。对 Okta 的断言来说，这是 600 秒。按这种方式衡量，每一个真实请求都会被拒绝，而且这个拒绝看上去就像一项正确的安全检查。

所以有效期从签发时间算起，也从当前时间算起；`nbf` 只按它本来的含义检查，即断言在此之前尚未生效：

```ts
const { exp, iat, jti } = claims;
if (typeof exp !== 'number' || typeof iat !== 'number')
	throw refused('lifetime');
if (typeof jti !== 'string' || !jti) throw refused('identifier');

const now = epochTime();
if (iat > now + clockTolerance) throw refused('issued_in_future');
if (
	exp - iat > MAX_LIFETIME_SECONDS + clockTolerance ||
	exp - now > MAX_LIFETIME_SECONDS + clockTolerance
) {
	throw refused('lifetime');
}
```

对照当前时间的那些检查，是人们常常漏掉的另一半。一个签发时间在明天、有效期五分钟的断言，完全能通过 `exp - iat` 的检查，单凭这一项衡量，它在一整天里都会被视为有效。拒绝未来的 `iat`，并限制从现在起剩余的时间，就堵上了这个口子，而且除了时间朝哪个方向流动之外，不需要在任何事情上信任签发方的时钟。

## 校验是常量，因为总会有人把设置关掉 {#the-checks-are-constants-because-someone-will-turn-a-setting-off}

一个能终止会话的端点，是一根能撬动整个员工队伍的杠杆。攻击者要拉动它，所需的输入是提供商的 issuer、我们在该提供商处的客户端 ID，以及某个用户在那里的 subject，而这些都不是秘密。所以这个端点上的每一项校验都按照请求带有敌意来写，因为将来到达它的请求中，有相当一部分确实会带有敌意。

Keycloak 8 月份的 CVE-2026-18569 是我时常放在眼前的案例。它的后端通道登出接收端，对于运维者关闭了签名校验的任何提供商，都会接受用 `alg: none` 签名的登出令牌。我不认为有人会在生产环境中故意关闭签名校验。我猜他们是为了调试一个连不上的提供商而关掉了一次，然后就忘了。所以在我们的服务器中，可接受的算法集合是一个常量，只包含非对称算法，再与提供商公布的算法取交集，没有任何提供商、桶或实例级设置能够扩大它。`none` 和所有 `HS*` 都会被拒绝，后者是因为除了提供商之外，任何人都不应持有签署这些令牌的密钥。

其余校验遵循同样的规则。提供商按 issuer 和客户端 ID 两个独立的值来查找，绝不拼成一个组合键，因为 Keycloak #42209 曾让任何别名中含有点号的提供商的代理登出（brokered logout）失效。`aud` 必须恰好是这个端点。`exp`、`iat` 和 `jti` 都是必需的，每个 `jti` 只接受一次，记录在一个由桶和提供商构成、以分隔符结尾的命名空间下，因为重放记录的 ID 是命名空间与 `jti` 直接拼接（中间没有任何分隔）后的哈希。未选择启用的提供商会被以 `403` 拒绝，但只在它完成认证之后，所以这个拒绝不会向未认证的调用方透露哪些提供商已启用。此外，认证失败的凭据会计入严格的按来源限流，与 SCIM 端点使用的是同一个计数器。

## 任何人都能戳的密钥缓存，需要找回冷却期 {#a-key-cache-that-anyone-can-poke-needs-its-cooldown-back}

还有一个陷阱，它在密钥缓存里，而不在校验里。在联合登录路径上，我们的服务器关闭了 jose 在两次重新获取提供商密钥集之间的三十秒冷却期。我们关掉它，是因为一致性测试套件的密钥轮换测试显示，每次上游轮换后，登录都会失败半分钟，而冷却期在那里什么也防不住：ID 令牌是从提供商自己的令牌端点读取的，所以只有提供商才能出示一个未知的 `kid`。

撤销请求恰恰相反。任何人都可以发送一个，带上任意他们想要的 `kid`，而没有冷却期的缓存会为每个未知的 `kid` 重新获取提供商的密钥。这会把我们的服务器变成一台对准客户身份提供商的反射器，每个伪造请求触发一次获取。所以同一个提供商有两个密钥缓存，用于所出示 JWT 的那一个保留了冷却期：

```ts
export function presentedKeySetFor(jwksUri: string): RemoteKeySet {
	const existing = presentedSets.get(jwksUri);
	if (existing) return existing;
	/* (the bound on how many providers are held is left out here) */
	/* jose's default 30 s cooldown: a genuine rotation is honoured once per cooldown. */
	const created = createRemoteJWKSet(new URL(jwksUri), {
		[customFetch]: fetchThroughBoundary
	});
	presentedSets.set(jwksUri, created);
	return created;
}
```

代价是 Okta 那边一次真实的轮换，每三十秒最多被采纳一次，而在这个窗口内带着新 `kid` 到达的撤销请求会被拒绝。与一个按指令就去获取密钥的端点相比，我每次都会选择这个取舍。

## 核心只建一次，草案作为插件 {#build-the-core-once-and-the-draft-as-a-plugin}

这一切之下的核心做三件事，并且对 Okta 一无所知：认证这个桶的一个上游提供商，决定该提供商可以指名谁，以及终止那个人的访问。全局令牌撤销模块只提供这些：哪个声明携带我们的客户端 ID、它的受众（audience）、它接受的令牌类型、一个重放命名空间，以及由哪个提供商选项来准入它。

这种拆分几乎立刻就回本了。来自 Keycloak、Auth0 和 Ping 的入站后端通道登出是同一个核心上的第二个模块，它继承了上面所有的拒绝规则，一条都不用重述。它唯一需要改变的，是我们的客户端 ID 放在哪里：登出令牌把它放在 `aud` 中，Okta 的断言把它放在 `sub` 中。这一点由格式声明，而不是靠猜，因为猜测会让令牌自己选择由哪个提供商来评判它。后端通道登出已经在真实的 Keycloak 26.8.0 上运行过。如果哪天有提供商真的发送 CAEP `session-revoked` 事件，那将是第三个模块。

## 我什么时候会开启它 {#when-i-would-turn-it-on}

如果一个部署的客户在使用带 Identity Threat Protection 的 Okta，并期望 Universal Logout 能覆盖每一个应用，我会为它开启，同时把这个开关注明为实验性功能，并在第一周安排专人盯着拒绝事件。其他所有地方我都会让它保持关闭，因为一个你不需要的端点，就是又多了一条进来的路。

而且我会如实说明它的现状，就像我在这里尽力做的那样。它还没有在真实的 Okta 组织上运行过；那需要 Identity Threat Protection，而测试套件是用一个桩提供商的密钥来重放 Okta 文档中描述的请求。Okta 在文档中把它的 `sub` 写作 `client_id/appInstanceId`，这可能并不是提供商配置中使用的那个裸客户端 ID；而一个用自定义授权服务器的 issuer 配置的提供商，可能与 Okta 请求中携带的组织 issuer 不匹配。这两点都只有真实运行才能定论。通常与之配套的 SCIM 一侧也有自己的缺口：Okta 的 CRUD 测试还没有运行，也没有 `/Bulk`。这些都还没有提交认证。如果草案复活并发生变化，模块会随之变化。如果它就此死去，Okta 大概会转向别的东西，而核心仍然是值得写下的那一部分。
