Токен, открывший все инструменты MCP-сервера, был выдан для внутренней вики.

Сервер сделал то, что делает большинство первых попыток. Он загрузил открытые ключи провайдера
идентификации, проверил подпись и срок действия, прочитал из полезной нагрузки subject и счёл запрос
аутентифицированным. Все эти проверки прошли, потому что токен был подлинным. Это был совершенно
нормальный токен для вики, а MCP-сервер так и не спросил, для кого он. Любой, у кого был любой токен
этого провайдера, выданный для чего угодно, мог получать список инструментов и вызывать их от имени
того, кто был указан в токене.

Именно эту ошибку и призвана предотвратить спецификация авторизации MCP, и стоит её однажды увидеть,
как остальная спецификация перестаёт выглядеть новым протоколом и начинает выглядеть тем, чем является:
обычным сервером ресурсов OAuth 2.1, у которого шаги обнаружения записаны так, чтобы клиент, не знающий
ничего, кроме URL, смог добраться до токена. Я провёл немало времени на стороне сервера авторизации, и мой
итог такой: это три документа и одно утверждение, и почти все реальные проблемы — в
этом одном утверждении.

## Три документа и одно утверждение {#three-documents-and-one-claim}

Хост агента знает одно: URL вашего MCP-сервера. Отсюда ему нужно узнать, кто вас защищает, как
разговаривать с этим сервером авторизации и как представиться самому, а затем вернуться с токеном,
который предназначен вам и никому больше. Каждое из этого — документ, а последнее — утверждение
(claim) в токене.

Шаг 2 — единственная часть всего этого, которую спецификация делает для MCP-сервера обязательной
(MUST), и это две строки. Когда запрос приходит без токена или с токеном, который вы отклоняете, вы
отвечаете 401 и сообщаете, где лежат ваши метаданные:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         scope="mcp:tools-basic"
```

А сами метаданные — это JSON-документ по RFC 9728, в котором сказано, кто вас защищает:

```json
{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://auth.example.com/acme"],
  "scopes_supported": ["mcp:tools-basic"],
  "bearer_methods_supported": ["header"]
}
```

Всё дальнейшее — забота сервера авторизации и клиента. Клиент берёт из документа издателя (issuer),
загружает метаданные этого сервера по well-known-адресам, которые определяют RFC 8414 и OpenID Connect
Discovery, и обязан попробовать оба, потому что спецификация требует от сервера публиковать только
один. Затем он выполняет обычный authorization code flow с PKCE, а в запросе авторизации и в запросе
токена передаёт один параметр, который на практике совсем не обычен, хотя RFC на него существует с
2020 года.

## Весь смысл — в параметре resource {#the-resource-parameter-is-the-whole-point}

RFC 8707 позволяет клиенту сказать, для чего ему нужен токен. Спецификация MCP делает этот параметр
обязательным в обоих запросах, и именно он превращает «токен от провайдера» в «токен для этого
MCP-сервера». Сервер авторизации выпускает токен с этим URI в качестве аудитории, а MCP-сервер
отклоняет любой токен, аудитория которого не совпадает в точности с его собственным идентификатором.
Именно на этой проверке срезается токен вики, и только она его бы и остановила.

Вот что сервер возвращает для показанного выше потока, в декодированном виде:

```json
{
  "iss": "https://auth.example.com/acme",
  "aud": "https://mcp.example.com/mcp",
  "sub": "248289761001",
  "client_id": "https://host.example/client.json",
  "scope": "mcp:tools-basic",
  "iat": 1759226400,
  "exp": 1759227300,
  "jti": "o1S6Qw3bH9c_UZL0"
}
```

Проверка на стороне MCP-сервера — это четыре утверждения, и два из них вы должны указать сами, потому
что JWT-библиотека не может их угадать:

```js
import { createRemoteJWKSet, jwtVerify } from 'jose';

const keys = createRemoteJWKSet(new URL('https://auth.example.com/acme/jwks'));

export async function principalFor(authorization) {
	const token = authorization?.replace(/^Bearer /i, '');
	if (!token) return null;
	const { payload } = await jwtVerify(token, keys, {
		issuer: 'https://auth.example.com/acme',
		audience: 'https://mcp.example.com/mcp'
	});
	return { subject: payload.sub, scopes: (payload.scope ?? '').split(' ') };
}
```

Подпись и `exp` — забота библиотеки. `issuer` и `audience` — ваша, и именно второе первая попытка и
упустила. Любая библиотека на любом языке выполняет те же четыре проверки; форма этого вызова и есть
чек-лист.

Дольше всего я осознавал другое: одна и та же строка теперь встречается в трёх местах, которые пишут
три разные стороны, и во всех трёх она должна быть одной и той же строкой. MCP-сервер публикует её в
своих метаданных как `resource`. Оператор сервера авторизации объявляет её идентификатором защищённого
ресурса. Клиент отправляет её как `resource`, а токен несёт её как `aud`. Сравнение точное, после
приведения к каноническому виду, и точное намеренно: никакого совпадения по префиксу, никакого «токен
для родительского пути годится и для дочернего», потому что именно так токен одной интеграции и
начинает работать в другой.

Канонизация — то место, где в нашей первой версии была ошибка, которую нашло рассуждение, а не тесты.
Спецификация говорит, что клиентам следует использовать форму без завершающего слеша, а серверам
следует принимать схему или хост в верхнем регистре, поэтому мы приводим к каноническому виду и
объявление, и запрос одной функцией, и эта функция принимает опцию для ресурса, у которого слеш значим.
Ошибка была в том, что при сравнении запрос канонизировался с опциями по умолчанию, а объявление было
сохранено с оставленным слешем, так что слеш срезался только с одной стороны, и ресурс, объявивший слеш
значимым, схлопывался со своим двойником без слеша. Обе стороны должны проходить через одну и ту же
функцию с одними и теми же опциями, и если это звучит очевидно — мне это тоже было очевидно. Задним
числом.

И ещё одно об аудитории: именно она целиком и делает объявленный ресурс безопасным в роли данных. В
нашем сервере объявить MCP-сервер — значит заполнить форму в консоли: идентификатор, название для
экрана согласия, scope (области доступа), которые он распознаёт. Ничего не перезапускается и код не
меняется, а объявление читается при каждом запросе токена, без кэша перед ним, потому что удалённое
объявление должно остановить выдачу на следующем же запросе, а не когда истечёт какая-нибудь
мемоизация. Этот урок мы однажды уже усвоили — с кэшем клиентов, который отдавал административной
плоскости устаревшего клиента, — и учить его повторно не требовалось.

## Кто такой клиент, когда некому ввести client id {#who-the-client-is-when-there-is-nobody-to-type-a-client-id}

У хоста агента есть URL и нет места, куда вы могли бы вставить идентификатор клиента. Раньше первым
ответом спецификации была динамическая регистрация клиентов: клиент отправляет POST-запрос с описанием
себя, получает обратно `client_id`, а сервер авторизации копит по записи на каждый хост, который
когда-либо подключался. Текущая редакция помечает это как устаревшее и ставит на первое место Client ID
Metadata Documents — по-моему, это верное решение и одновременно та часть спецификации, из-за которой
больше всего стоит нервничать.

Идея в том, что `client_id` сам является HTTPS-URL, а по этому URL лежит JSON-документ с описанием
клиента:

```json
{
  "client_id": "https://host.example/client.json",
  "client_name": "Example Agent Host",
  "redirect_uris": ["http://127.0.0.1:52123/callback", "https://host.example/oauth/callback"],
  "token_endpoint_auth_method": "none",
  "grant_types": ["authorization_code", "refresh_token"]
}
```

Сервер авторизации загружает его по требованию, проверяет и ничего не сохраняет. Ни эндпоинта
регистрации, ни таблицы клиентов, которая прирастает на одну запись с каждым ноутбуком, а имя клиента на
экране согласия берётся из документа, который оператор клиента контролирует на домене, которым он
доказуемо владеет.

Цена этого в том, что посторонний без всякой аутентификации теперь может заставить ваш сервер
авторизации отправить HTTP-запрос на URL по своему выбору. Все меры защиты от этого должны быть на
сервере, и у нас это один модуль, который знает о сети и ни о чём больше: он отказывает частным,
loopback- и link-local-диапазонам адресов, сравнивая адреса как числа, а не как текст, потому что
парсер URL охотно перепишет IPv4-mapped IPv6-адрес в форму, которую строковая проверка пропустит; он
следует редиректам вручную и перепроверяет каждый переход; он прекращает чтение на пяти килобайтах; и
он ограничен по времени. По умолчанию функция выключена, и причина — ровно та фраза о постороннем. Когда
документ получен, проверки короткие, и каждая закрывает конкретный трюк: `client_id` внутри документа
должен побайтно совпадать с URL, так что размещение документа с чужим идентификатором ничего не даёт;
`redirect_uris` должен присутствовать и быть непустым; симметричный секрет клиента отклоняется, потому
что секрет в общедоступном документе — уже не секрет; а метод аутентификации на основе ключей должен
указывать, где лежат его ключи.

Часть, которую я назвал бы по-настоящему нерешённой, — loopback. Нативный хост агента ждёт callback на
`127.0.0.1` на каком-то порту, поэтому в его документе указан loopback-редирект. Документ доказывает,
что его автор контролирует домен. Он не может доказать, какой локальный процесс слушает этот порт.
Злоумышленник на той же машине может предъявить `client_id` настоящего хоста, занять свой порт, и
пользователь увидит на экране согласия имя настоящего хоста. Спецификация об этом знает, говорит, что
серверу следует предупреждать, и на этом останавливается. Для обычного ресурса мы несём этот риск так
же, как все. Для единственного места, где клиент, идентифицированный документом, может получить
административные полномочия над самим сервером авторизации, мы превратили предупреждение в блокировку:
документ, предлагающий только loopback-редиректы, нельзя допустить, пока администратор не подтвердит
словами, чего это не доказывает.

## Каких пользователей впускает агент {#which-users-an-agent-signs-in}

Вот вопрос, которого спецификация не задаёт, потому что исходит из того, что один сервер авторизации
защищает один MCP-сервер для одной совокупности пользователей, а сервер авторизации выглядит иначе, как
только им начинает пользоваться больше одной команды.

Допустим, сервер обслуживает несколько тенантов, у каждого свои пользователи, и приходит хост агента,
идентифицированный документом метаданных. Он не принадлежит ни одному тенанту. Он — URL. Чьих
пользователей он впускает? Мы остановились на том, что решает ресурс: администратор тенанта объявил
этот MCP-сервер в одном из своих проектов, и запрос, называющий этот ресурс, ведёт на вход пользователей
этого проекта. Это безопасно по причине, которую стоит сформулировать точно. Этот вариант создал не
клиент, а администратор, в проекте, которым он владеет, так что параметр выбирает среди объявлений
оператора и не может изготовить новое.

Безопасно, то есть, против злоумышленников без учётной записи в консоли. Любой, у кого она была, мог
объявить что угодно, идентификаторы были уникальны в пределах всего экземпляра, и побеждал первый. Так
враждебный тенант мог объявить чужой MCP-сервер, оставить настоящему владельцу вечный конфликт и
направить пользователей этого сервера в свой бакет. Первое исправление заставляло каждое объявление
доказывать себя: загружать собственные метаданные ресурса и проверять, что в них назван этот издатель.
Исправление естественное, но оно же отвергало каждый MCP-сервер во внутренней сети, на localhost во
время разработки или ещё не развёрнутый. Оно продержалось день.

Его место заняли пространства имён, и именно такую схему я теперь посоветовал бы каждому, кто это
строит. Тенант с собственным адресом — это отдельный издатель со своими ключами подписи, а идентификатор
ресурса уникален только в пределах издателя. Два тенанта могут объявить один и тот же MCP-сервер, и ни
один никогда не увидит объявление другого, потому что любой поиск объявления читает только пространство
имён того адреса, на который пришёл запрос. Объявление в собственном пространстве имён не делает вообще
никаких исходящих запросов, поскольку оно может быть только утверждением о ваших собственных
пользователях. А единственное по-настоящему общее пространство имён — корневой издатель, на котором
обслуживается каждый тенант без собственного адреса, — принимает объявления только от
суперадминистратора, потому что там метаданные ресурса могут сказать, что доверяют издателю, но всё
равно не могут сказать, какому из этих тенантов ресурс принадлежит. Никакое доказательство не закрывает
там захват чужих идентификаторов, поэтому пробовать не позволено никому, кроме оператора.

Ещё три дыры в той же области. Первые две вида «вызывающий код забыл передать ресурс», и обе стоит знать,
потому что это ровно тот род ошибок, который такая архитектура делает возможным. Резолвер учётных
записей находил пользователей не того тенанта, что шаг входа, потому что вход передавал ресурс, а
резолвер — нет, и симптомом был 500 на экране согласия, а не отказ. А двери пароля, сброса и регистрации
определяли политику только по клиенту, так что до тенанта, чьи пользователи входят только через внешнего
провайдера, можно было добраться с паролем через объявленный ресурс. Обе закрыты тем, что ресурс стал
обязательным аргументом, так что пропуск больше не проходит проверку типов. Если вы возьмёте из этого
раздела одно инженерное правило, возьмите это: когда параметр выбирает тенанта, сделайте вызов функции
без него невозможным.

Последняя — машинные токены. Конечный пользователь даёт согласие, поэтому любой клиент, в том числе
ничей, может попросить у человека токен к объявленному ресурсу. Токен client credentials ни у кого не
спрашивает. Пока мы этого не заметили, любой конфиденциальный клиент любого тенанта или клиент,
зарегистрировавший себя сам, мог попросить у эндпоинта токенов тенанта-жертвы токен с ресурсом жертвы в
качестве аудитории и с издателем жертвы — и получить его. Теперь машинный токен для объявленного ресурса
выдаётся только клиенту проекта, который этот ресурс объявил. В спецификации об этом ничего нет. И не
могло быть: это вопрос мультитенантности.

## Список scope — это выдача, а не меню {#the-scope-list-is-a-grant-not-a-menu}

Одна мелочь, которая меня удивила. Если ваш challenge в `WWW-Authenticate` не содержит `scope`,
спецификация велит клиенту запросить все scope из вашего `scopes_supported` и называет это намеренным:
универсальный клиент не может разумно выбирать среди имён, которых не понимает. Так что длинный список в
метаданных — не каталог вариантов, а то, что получит каждый агент, который когда-либо подключится.
Укажите в challenge тот scope, который действительно нужен вашим инструментам, держите
`scopes_supported` минимальным для базового использования и просите больше через 403 и
`insufficient_scope`, когда привилегированный инструмент вызывается впервые. Клиент обязан считать
scope из challenge определяющим и сам накапливать scope при последовательных повышениях (step-up),
поэтому сервер авторизации может не хранить об этом никакого состояния. Наш собственный
административный MCP-эндпоинт объявляет `openid` и больше ничего, потому что его полномочия берутся из
членства администратора в группах, а не из scope, а scope, который эндпоинт никогда не
проверяет, публиковать незачем.

## Два вопроса, которые спецификация оставляет вам {#two-questions-the-specification-leaves-to-you}

Первый — формат токена, и спецификация старательно его не решает. MCP-сервер должен отклонять токены,
предназначенные не ему, «или иным образом проверять, что он является их предполагаемым получателем», а
это допускает и самодостаточный токен, проверяемый по опубликованным ключам, и непрозрачный, проверяемый
через интроспекцию. По умолчанию мы используем самодостаточный токен со временем жизни пятнадцать минут,
потому что интроспекция обязывает ваш MCP-сервер иметь собственные учётные данные, а в десятиминутном
руководстве по настройке для этого шага нет места. Плата в том, что самодостаточный токен действителен,
пока не истечёт. Если отозванный токен должен перестать работать за секунды, а не за минуты, объявите
ресурс непрозрачным (opaque), дайте своему MCP-серверу собственного клиента и платите за интроспекцию
при каждом вызове. Ни один из ответов не ошибочен; ошибка — не знать, какой из них вы выбрали.

Второй — проблема confused deputy: посредник, которому доверены чужие полномочия, обращают против их
владельца. Решать её не серверу авторизации.
MCP-сервер, который проксирует сторонний API с одним статическим client id, динамически регистрирует
собственных MCP-клиентов и пересылает коды без собственного экрана согласия, — это та самая
конфигурация, которую руководство по безопасности разбирает атака за атакой. Защита — согласие для
каждого клиента на прокси, до начала стороннего потока, и проверка аудитории, чтобы токен, полученный
прокси, никогда не передавался дальше как есть. Всё, что я описал в спецификации, в этом помогает, и
ничто из этого не делает работу за вас.

Чего я пока не знаю — как на практике сложится политика доверия к документам метаданных. Спецификация
позволяет серверу авторизации принимать любой HTTPS `client_id`, вести белый список доменов или
применять проверки репутации, и каждый вариант — своя поверхность для фишинга, поскольку имя на экране
согласия — это то, что написано в документе. Открытость по умолчанию — то, на чём держится экосистема,
а белые списки — то, чего захочет корпоративный заказчик, и я подозреваю, что ответ — и то и другое,
для каждого тенанта отдельно, а это ещё один вопрос, который спецификация так и будет оставлять тому,
кто эксплуатирует сервер.

Если хотите увидеть всю картину от начала до конца, руководство [Защита MCP-сервера с помощью
OAuth](/ru/docs/get-started/protect-your-mcp-server/) примерно за десять минут проводит через
объявление, оба документа, проверку токена и оба доказательства. Две настройки, которые решают, как хост
агента может себя идентифицировать, — это
[`clientIdMetadataDocument.enabled`](/docs/reference/settings/#clientIdMetadataDocument.enabled)
и [`registration.enabled`](/docs/reference/settings/#registration.enabled), а в
[справочнике эндпоинтов](/docs/reference/endpoints/) указано, что отвечает каждый URL обнаружения.
